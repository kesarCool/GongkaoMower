# 微信小游戏资源分包原理

## 一、你的游戏现在有哪些资源？

构建产物 `Build/minigame/` 下有三类东西：

```
minigame/                          ← 微信小游戏根目录
├─ minigame/                       ← 小游戏代码包（会被上传到微信审核）
│  ├─ game.js                      # 入口
│  ├─ webgl.wasm.framework.unityweb.js  # Unity 引擎 JS 桥
│  ├─ unity-sdk/                   # 微信 SDK JS
│  ├─ weapp-adapter.js             # 微信适配层
│  ├─ wasmcode/          [分包]    # WebAssembly 代码（5.3M br）
│  ├─ data-package/      [分包]    # Unity 场景/贴图/字体等资产（18M br）
│  └─ Assets/              ← 这是你手动拷贝进去的，不在分包体系里！
│     └─ Audio/
├─ webgl/                          # Unity 原始 WebGL 构建产物（不上传）
└─ project.config.json             # 微信项目配置
```

## 二、三种资源来源

微信小游戏中，Unity 代码能拿到的资源有三种来源：

### 来源 1：代码包（上传到微信服务器）

`minigame/minigame/` 下的所有文件，打包后上传到微信审核。用户下载小游戏时，这些文件会随首次加载一起下载。

- **主包**（≤4MB）：game.js、框架 JS、SDK、weapp-adapter 等
- **分包**：wasmcode/、data-package/
  - 普通分包无单包大小硬性上限，独立分包 ≤4MB
  - **总包（主包 + 所有分包）上限**：≤20MB（无版号/未开通虚拟支付），≤30MB（有版号且开通虚拟支付后）

优点：用户一打开就有，不需要网络额外下载。
缺点：占 4M 主包限额，审核不过直接打回。

### 来源 2：CDN 远程资源（不走微信审核）

放在你自己服务器（或腾讯云 CDN）上的文件。用户运行时按需下载。

优点：不占包体限额，无限大小。
缺点：需要额外维护 CDN，用户要等下载，有流量成本。

### 来源 3：用户本地缓存（wx.env.USER_DATA_PATH）

运行时从 CDN 下载的文件会缓存到用户手机本地。下次启动不再下载，直接从缓存读。微信管理缓存淘汰策略。

## 三、你的游戏实际是怎么加载资源的

### Unity 构建产物的加载流程

```
用户打开小游戏
  │
  ├─ 1. 下载主包（~1.1M）          ← game.js + 框架 JS + SDK
  ├─ 2. 下载分包 wasmcode（5.3M）  ← WebAssembly C# 代码
  ├─ 3. 下载分包 data-package（18M）← 场景/贴图/字体/Prefab/SO
  │
  ├─ 4. Unity 引擎启动
  │     ├─ 场景里的 Prefab 引用 → 从 data-package 里读
  │     ├─ Resources.Load("xxx") → 从 data-package 里读
  │     ├─ 字体/TMP Font → 从 data-package 里读
  │     └─ StreamingAssets → ？？？
  │
  └─ 5. 游戏运行
```

### data-package 里面有什么？

Unity Build 时会把所有**被引用的资源**打进 `webgl.data`（即 data-package 分包）：
- 场景里拖上去的 Prefab / 贴图 / 材质
- `Resources/` 目录下的所有文件（自动打包）
- TMP 字体 atlas
- 所有 ScriptableObject（如 SkillDef、CardDeck、AudioCatalog）
- Unity 内置资源（shader、默认贴图等）

**没有被引用的不会进包**。`Assets/Res/` 下的文件如果没有被任何场景/Prefab/SO 引用，就不会出现在 data-package 里。

### StreamingAssets 的特殊性

`Assets/StreamingAssets/` 目录下的文件 **不进 data-package**。Unity 会把它们原样拷贝到构建输出目录。在微信小游戏中：

```
Unity Build → Build/webgl/StreamingAssets/Audio/xxx.mp3
                                     ↓
WX SDK 转换 → 放到 minigame 根目录（手动 or 构建脚本）
                                     ↓
运行时路径 → Application.streamingAssetsPath + "/Audio/xxx.mp3"
                                     ↓
微信 WebGL 里 → UnityWebRequest 加载（走本地文件或 CDN）
```

**关键点**：StreamingAssets 文件不在微信分包体系里。你需要手动把它们处理到能访问的位置。

## 四、音效为什么出问题

你的音效文件经过了这条路：

```
Assets/Res/Audio/xxx.mp3                ← 源文件（不进包）
         ↓ AudioBuildCopy
Assets/StreamingAssets/Audio/xxx.mp3    ← Unity 构建时拷贝到这里
         ↓ Unity Build
Build/webgl/StreamingAssets/Audio/xxx.mp3
         ↓ AudioBuildCopy
Build/minigame/minigame/Assets/Audio/xxx.mp3  ← 手动拷到代码包根目录
         ↓ 运行时
WeChatAudioBackend.Play()
  → ctx.src = "Audio/Battle/PlayerSkill/xxx.mp3"
  → inner-audio.js getFullUrl() 拼接
    cdnPath = "/Assets" (GameGlobal.manager.assetPath)
    结果 URL = "/Assets/Audio/Battle/PlayerSkill/xxx.mp3"
  → wx.downloadFile("/Assets/Audio/Battle/PlayerSkill/xxx.mp3")
  → 微信本地服务器返回文件 ✓（因为文件在 minigame/minigame/Assets/Audio/ 下）
```

**所以音效文件不需要 CDN**。它们在微信 dev server 下作为本地文件被访问。但前提是文件被正确放在了 `minigame/minigame/Assets/` 路径下。

## 五、其他资源能不能像音效一样放 StreamingAssets？

**能，但不推荐。**

StreamingAssets 的适用场景：
- 超大街机包体外的额外资源（如高清贴图 DLC）
- 需要运行时替换的文件（配置、热更脚本）
- 音效（因为 Unity Audio 在 WebGL 下对 Resources 加载支持差）
- 你不会每次都用的资源，避免打进 data-package 撑大包体

StreamingAssets 的问题：
- **不进 data-package** → 不在微信分包体系里 → **你需要自己管部署**
- **不进微信的 Br 压缩** → 文件大
- **不进微信的缓存管理** → 每次启动可能重新下载
- **代码包放 StreamAsset** → 占主包 4M 限额 → **审核可能不过**

## 六、你的资源现状对照

| 资源类型 | 存放位置 | 进哪个包 | 大小 | 加载方式 |
|----------|---------|---------|------|---------|
| 场景 Prefab | Scene 引用 | data-package | 3.3M+ | Unity 自动 |
| 字体 | Resources/Fonts | data-package | ~2M(Br压缩后) | Resources.Load |
| 地图瓦片 | Map/GeneratedTiles | data-package | 68K | 场景引用 |
| UI 贴图 | Res/image | data-package | 938K | 场景/Prefab 引用 |
| 特效贴图 | Res/Textures | data-package | 3.9M | 材质引用 |
| 技能 SO | ScriptableObject | data-package | ~10K | Resources.Load |
| 表格数据 | Resources/Data | data-package | 59K | Resources.Load |
| **音效** | StreamingAssets | **主包代码目录** | ~1.5M | WXInnerAudioContext |

**音效是你唯一不在 data-package 的资源**。

## 七、你的音效为什么不进 data-package 的设计是对的

Unity Audio 在 WebGL 下的 Resources 加载极度不可靠：
- `Resources.Load<AudioClip>()` 在 WebGL 下需要完整解压到内存
- 微信 WebGL 底层对 AudioContext 有数量限制
- 微信官方的推荐做法就是用 `wx.createInnerAudioContext`（即 WX SDK 的方案），它绕过 Unity 的 Audio 系统，直接调用微信的音频 API

所以音效走 `StreamingAssets + WXInnerAudioContext` 是正确的架构选型。

## 八、你的 audio 文件实际在哪？为什么改了三版路径

```
微信小游戏根目录 = Build/minigame/minigame/
微信 dev server 的根 = minigame/minigame/

运行时 inner-audio.js 请求:
  路径: /Assets/Audio/Common/sfx_button_click.mp3
  映射: minigame/minigame/Assets/Audio/Common/sfx_button_click.mp3

第一版 (Build/minigame/Audio/)          ← 少了两层，404
第二版 (Build/minigame/Assets/Audio/)    ← 少了一层 minigame/，404  
第三版 (Build/minigame/minigame/Assets/Audio/) ← 正确
```

## 九、上线后音效怎么办？

上线后音效有两种选择：

**方案 A：跟着代码包上传（当前做法）**
- 音频文件随代码包上传微信审核
- 优点：不需要 CDN，用户即开即用
- 缺点：V1.5M 音频在主包里 → **主包从 1.1M 膨胀到 2.6M**，仍在 4M 内，暂时安全。后续音效多了可能超标。

**方案 B：放 CDN 上**
- `DATA_CDN` 配置指向你的 CDN 地址
- 音频文件部署到 CDN
- inner-audio.js 自动拼接：`https://cdn.xxx.com/Assets/Audio/...`
- 下载后缓存到本地，下次不重复下载
- 优点：不占包体
- 缺点：需要 CDN，首次有下载延迟

**当前你的 DATA_CDN 是空的**（game.js 中 `DATA_CDN: ''`），所以 inner-audio.js 用本地路径。如果后续设了 CDN，音频路径自动切到 CDN URL，不需要改任何 C# 代码。

## 十、总结

| 问题 | 答案 |
|------|------|
| 音效必须放 CDN 吗 | 不必须。当前放代码包本地 = 能用。上线后可选 CDN |
| 其他资源能用 StreamingAssets 吗 | 能，但不推荐。data-package 已自动处理 99% 资源 |
| StreamingAssets 和 data-package 的区别 | data-package 自动打进分包+Br压缩。StreamingAssets 手动管理，不进分包 |
| 你的音效放哪里正确 | `minigame/minigame/Assets/Audio/`，对应运行时 `/Assets/Audio/...` |
| 音效路径为什么这么绕 | 因为 WX SDK 的 `cdnPath=/Assets` + `getFullUrl` 自动拼接，约定俗成 |
