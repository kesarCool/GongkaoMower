## 一、音频：为什么不进 data-package、现在为什么进了

### 之前
音频文件放在 `Assets/StreamingAssets/Audio/`。Unity 构建时 StreamingAssets 不进 data-package——它被原样拷贝到构建输出目录，由开发者自行部署。微信环境下有三种加载路径：CDN 下载、用户缓存、代码包本地文件。我们踩了每种路径的坑：
- InnerAudioContext 不支持代码包本地文件
- wx.downloadFile 不接受本地路径
- streamingAssetsPath 在微信里指向 CDN（`game.weixin.qq.com`），本地开发文件不在那里

### 现在
音频移到 `Assets/Resources/Audio/`。Unity 自动把 Resources 目录打进 data-package。加载方式从 `InnerAudioContext` + `UnityWebRequest` 改为 `Resources.Load<AudioClip>()`，彻底绕过微信音频桥。

### 代价
11 个音频文件共 464KB。data-package 只增加约 300KB（br 后）。**可接受。**

## 二、当前问题清单

### 2.1 字体：9MB Editor 文件，实际构建贡献 ~1.8MB

| 指标 | 值 |
|------|-----|
| Editor 文件大小 | 9.0MB（hex 编码，构建时用二进制） |
| Atlas 原始 | 2048×2048 Alpha8 = 4MB |
| 字形表 | 1694 字符 × ~200B ≈ 340KB |
| 构建后 raw | ~4.3MB |
| Br 压缩后 | **~1.8MB**（占 data 约 11%） |

**9MB 是 YAML hex 序列化的 Editor 假象，构建时 Unity 提取二进制 atlas 打进包。** 字体占比 11%，不是头号问题。之前报告估算有误。

### 2.2 构建配置脏数据

`ProjectSettings/EditorBuildSettings.asset` 中仍引用 `SampleScene.unity`，但文件已删除。Unity 构建时会跳过，但配置项残留。

### 2.3 data-package 80% 占用

16M / 20M。微信单分包上限 20M，只剩 4M 额度。加新资源（贴图、动画、更多音效）随时可能超标。**这不是线上紧急问题，但后续加任何中大型资源都危险。**

### 2.4 data-package 真实构成

| 成分 | Br 压缩后 | 占比 |
|------|----------|------|
| Unity 内置(Shader/默认贴图) | ~3-4MB | ~22% |
| 场景资产(贴图/Prefab/SO) | ~6-8MB | ~44% |
| 字体 Atlas(4MB Alpha8) | ~1.8MB | 11% |
| IL2CPP metadata | ~1-2MB | ~10% |
| 音效(464K raw) | ~0.3MB | 2% |
| 表数据等 | ~1MB | 6% |
| **合计** | **~16MB** | — |

最大可以优化的部分是**场景资产**——贴图压缩、删未用特效纹理、清理冗余 Prefab。

### 2.5 音效在 WebGL Editor 下不可用

`Resources.Load<AudioClip>()` 在 Editor 里不走 WebGL 路径，走的是 `if (TryLoadImportedClipEditor(...))`——从 `Assets/Res/Audio/` 直接读。但音频已经不在 `Res/Audio/` 下了——**Res 目录里的音频和 Resources 目录里的音频是两份，现在 Res 那份可能已经被删掉或没同步。** 验证：Editor 下 Play 有没有音效声音。

### 2.4 WeChatAudioBackend 成了死代码

`AudioService.CreateBackend()` 已改为永远返回 `UnityAudioBackend`。`WeChatAudioBackend` 整个类不再被实例化。但文件还在，里面 150+ 行代码成了维护包袱。下次有人改音频逻辑可能改错文件。

### 2.5 StreamingAssets/Audio 残留未清理

`Assets/StreamingAssets/Audio/` 还在——音频已经从 StreamingAssets 移到了 Resources，但旧目录和旧文件没删。这不会影响构建（StreamingAssets 不进 data-package），但属于脏数据，将来可能被误拷进包。

## 三、上线潜在问题

### 3.1 音频在真机上的兼容性

`Resources.Load<AudioClip>()` 在 WebGL 下依赖浏览器的 WebAudio API。微信 Mini Game 的 WebGL 实现了 WebAudio，但格式支持有差异：

| 格式 | 微信 WebGL 支持 |
|------|----------------|
| mp3 | ✅ |
| wav | ✅ |
| ogg | ⚠️ 部分机型不支持 |

你有 `.ogg` 文件（`sfx_enemy_die.ogg`、`sfx_skill_field_generator.ogg`）。建议全转成 `.mp3` 或保留 `.wav`，避免 ogg 在部分安卓上无声。

### 3.2 字体在微信上的兼容性

TMP SDF 字体在 WebGL 下工作正常，但微信 WebGL 的纹理压缩可能导致 SDF 边缘模糊。如果线上文字看起来糊，需要关掉微信的自动纹理压缩对字体 atlas 的处理。

### 3.3 加载顺序

`BattleLoading` 场景 → `Game` 场景。进入 Game 时 `AudioService.BootstrapCommonGroup()` 用 `RuntimeInitializeOnLoadMethod` 自动启动音频加载。如果音频加载阻塞了首帧渲染（WebGL 下 Resources.Load 是同步的），会有短暂卡顿。464KB 的同步加载应该感知不到，但后续音效多了就可能有感觉。

### 3.4 Build 目录文件锁

Windows 上反复出现 `IOException 文件被占用`。原因是构建过程中其他程序（VS Code、文件资源管理器、杀毒软件）持有 `Build/minigame/` 下的文件句柄。这不是 Bug，但值得在构建脚本里加一个 `rm -rf Build/minigame` 的前置步骤。

## 四、优化空间（按收益排序）

### T0: 清理 unused 特效纹理（省 ~500K）

`Assets/Res/Effect/_Effect/` 下有噪音纹理（noise_61、Noise63、lighting97）合计 ~400K。跑 `Tools/纹理优化分析` 确认是否被引用，未引用就删。

### T2: 纹理压缩批量应用（省 ~1M）

login_bg.png (498K)、pic_sl.png (206K)、pic_sb.png (153K)、logo.png (141K) 这些 UI 大图都没开 Crunched 压缩。全选 → Inspector 里改 Max Size=1024, Crunched ETC2, Quality=50。

### T3: ogg → mp3 统一格式

`sfx_enemy_die.ogg` 和 `sfx_skill_field_generator.ogg` → 转为 mp3。避免微信部分机型无声。不影响包体大小。

### T4: 删除 WeChatAudioBackend 死代码（省编译时间 + 清理维护心智负担）

`WeChatAudioBackend.cs` 不再被使用。连同相关辅助代码（`AudioPathUtility.ResolveWeChatSrc` 方法）一并删掉。

### T5: 清理 StreamingAssets 残留

删除 `Assets/StreamingAssets/Audio/` 目录和 `AudioBuildCopy.cs` 的自动拷贝逻辑。
