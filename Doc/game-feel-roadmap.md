# 游戏表现升级规划

更新：2026-10-24。依据当前 `feat/WeChatminigame` 分支的代码、角色配置和既有 UI。按用户后续调整，B（获得物品）与 C（升级、升阶和解锁反馈）已优先接入，Unity 验证通过；角色战斗动作单独安排。实施文件与验证边界见 `Doc/progression-feedback-implementation.md`。

## 建议的顺序

先完成弹仔一个角色的实机动作样板，同时确定统一奖励弹窗；随后实现角色升级、升阶、技能解锁反馈。样板验收后再扩展其余四个角色。保持当前数值、技能效果和获得物品规则，先提高已有内容的可感知程度。

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| A：角色动作样板 | 弹仔移动、左右朝向、持枪瞄准、真实开火后坐、受击；实机短视频 | 移动有节奏，枪口与弹道一致，切换朝向不倒枪、不出现两把枪，暂停时动作停止 |
| B：获得物品 | 共用 RewardRevealPanel，接兑换、广告奖励、成就、兑换码 | 一次领取只发放一次，多个物品一并展示，连续领取排队；背包浏览不弹奖励 |
| C：成长反馈 | 升级数字变化、等级提示、升阶揭晓、角色/技能解锁 | 真实前后数值可见；切页、切角色和快速操作不会串角色、重复播放或多扣资源 |
| D：扩展与验证 | 其余角色按武器差异接入，同构复用反馈资源，微信真机测试 | 五角色均可用；记录包体、峰值内存及战斗帧时间变化，再决定是否增加完整骨骼动画 |

## A：角色优先用轻量分件，Spine 作为后续选择

### 现状与切入点

- 五个角色目前都是单张 160×160 贴图，武器已画在身体里。五份武器配置中的独立 Sprite 都为空，因此 `CharacterAppearance.ApplyWeapon` 会直接返回。
- `CharacterAppearance.OnSkillCast` 只接受 AutoProjectile（ID 1），五角色起始技能实际为 7/8/12/9/10。已有的武器摆动接口尚未覆盖这些技能。
- `PlayerController` 已经有目标缓存、朝向与移动逻辑，可复用；摇杆与点击移动走不同路径，动作需要读取实际位移或统一移动状态。
- `PlayerHitFeedback` 会写 Body 的位置与缩放。新增移动动画若也写同一 Transform，会相互覆盖；需要分层隔离。

### 第一版的具体表现

1. **待机**：轻微呼吸，幅度低于移动状态，脚底阴影保持落地。
2. **移动**：按实际速度驱动起伏、侧倾和停止回正；不移动 Collider、生命条或角色根节点。
3. **瞄准**：枪朝当前攻击目标；无目标时沿最后有效方向或移动方向。左右切换时调整握点、枪的上下关系和层级，枪身保持正向。
4. **射击**：由实际生成弹丸的入口触发短促后坐、手臂回弹、枪口闪光。不能仅按冷却时间模拟，否则视觉与真正发射不同步。
5. **受击**：保留现有闪色/震动，和移动起伏分别作用于独立节点。
6. **主动技/大招**：只给现有真实释放事件加蓄势、短闪或武器动作，按角色与技能配置，不增加新的玩法。

建议层级：

```text
Player                   // 原有移动、碰撞、技能、血量
├─ Shadow                // 脚底固定
├─ ObjHp                 // 不跟随动作起伏
└─ VisualRoot            // 移动起伏和倾斜
   └─ HitRoot            // 受击偏移
      ├─ Body
      └─ WeaponPivot     // 瞄准转向
         └─ WeaponRecoil
            └─ WeaponSprite
```

最小美术交付为弹仔的无枪身体、独立枪与持枪手（允许合为一个手枪组件）、可复用小闪光和软阴影。当前 UI 立绘继续使用原整图；战斗使用独立分件，避免全局替换导致角色卡面缺枪。

**移动起伏仍然是整块身体运动，不等同于双腿迈步。** 如果实机仍像滑行，再补左/右腿和必要的遮挡补画，制作短循环跑步。先验收一个角色，避免重复此前下肢不协调的问题。追风等角色以自身武器结构设计动作，不强行套持枪动作。

实现时显式绑定 BodyRenderer、移动节点和受击节点，处理旧 `Find("Body")` 引用；战斗动作使用受 `Time.timeScale` 控制的时间，暂停冻结，角色切换或禁用时停止旧动画并归位。沿用现有目标缓存，不为武器额外逐帧遍历怪物。

### Spine Skill 调研结论

确实存在可试验的社区工具，但尚未在本机验证，不宜直接当作能交付自然动作的一键方案：

| 候选 | 能帮助的部分 | 当前边界 |
| --- | --- | --- |
| [Spine-SKILL](https://github.com/zxzAndyMAC/Spine-SKILL) | 指导拆件、绑定、动作设计、修正、视觉验收和可编辑交付 | 本身是工作流程指令，仍需要编辑器及执行工具，不自带一键图片转动画能力 |
| [spine-motion-mcp](https://github.com/nihatcagri44/spine-motion-mcp) | 对已有骨架编排关键帧、套基础动作、预览与导出 | 面向 Spine 4.2；Windows CLI 相关流程仍有作者标注的未验证项，默认步态不能保证膝盖和脚掌自然 |
| [spine_anim_mcp](https://github.com/K-ulucay/spine_anim_mcp) | 分层 PSD 建骨架和程序动作试验 | 当前真实图层像素提取仍在 roadmap，不能把占位预览当作角色原画交付，因此不选为正式美术流水线 |

证据：[Spine Skill 说明](https://github.com/zxzAndyMAC/Spine-SKILL#requirements-and-compatibility)、[spine-motion 测试边界](https://github.com/nihatcagri44/spine-motion-mcp/blob/main/TESTING.md)、[PSD 工具的未完成项](https://github.com/K-ulucay/spine_anim_mcp#roadmap)。Spine 官方 CLI 提供的是工程导入、导出与图集打包等自动化；运行时须与导出版本对应，见[官方 CLI 文档](https://esotericsoftware.com/spine-command-line-interface)及[Unity 运行时文档](https://esotericsoftware.com/spine-unity-download)。用户此前提供的参考动画 JSON 是 3.6.53，不能直接按 4.2 工具链处理。

建议这一轮先不用增加 Spine 运行时。后续如确实需要完整跑步、施法和表情，使用上述 Skill 规范工作流程，试验一个角色的编辑器保存重开、运行时播放、Unity 导入和真机性能闭环。只有这四步通过，才推广至五角色。

## B：统一“恭喜获得”弹窗

### 视觉方案

沿用现有奶油纸面、深棕字、彩色物品底板。标题“恭喜获得”，中间按物品数量居中排布；图标、名称、数量均有独立区域。多件时使用网格，较多物品允许滚动。下方“收下”或“继续”按钮。

- 0–0.15 秒：遮罩淡入，标题与面板轻微放大到位。
- 0.15–0.45 秒：物品依次弹出，间隔建议 0.04–0.07 秒，小幅回弹及稀有度光效。
- 点击可加速揭晓，所有物品可立即查看，正常领取不强制等待完整动画。
- 角色解锁或重大奖励可以复用同一数据与排队机制，使用更强的展示样式；普通金币领取保持简短。
- 音效遵守设置开关。复用现有字体、通用光斑和粒子，不新增字体库、整屏序列帧或长视频。

### 接入方式

业务成功发放并保存后，把本次实际奖励结果交给展示队列。建议数据为 `RewardRevealRequest(receiptId, source, items, presentationMode)`。展示层只读，不承担发放，收下、跳过、关闭和中断均不能再次加物品。

| 来源 | 当前可接入入口 | 本轮设计要求 |
| --- | --- | --- |
| 兑换/广告商品 | ShopView → ShopService.Purchase / ClaimAdReward | 广告期间锁定本次请求并保存商品快照，避免重复回调和列表刷新串商品 |
| 成就 | AchievementPanel → AchievementService.Claim | 使用服务返回的实际 rewardId/rewardCount，不写死“获得钻石” |
| 兑换码 | SettingsPanel → GiftCodeService.TryRedeem | 返回实际奖励结果，领取成功再展示 |
| 角色碎片解锁 | CharacterSelectionPanel → TryConsumeFragmentUnlock | 解锁展示只触发一次，不再附加一次发放 |
| 战斗结算 | BattleOutcomeCoordinator / GameResultPanel | 保留现有结算奖励展示，第一轮不再叠加同一份奖励弹窗 |
| 背包浏览 | BackPackPanel / ItemTooltip | 保持只读详情，不触发“获得” |

队列一次只展示一个弹窗，同一 receipt 去重；一次事务的同类物品合并，不随意合并独立的广告领取。receiptId 只负责展示去重，实际发奖的一次性仍由业务服务的限购、已领取标记和事务锁保证。

不要从 PlayerDataChangedEvent、全局金币/钻石收入或初始化修复产生的解锁事件自动推断领奖，因为初始化、修正和一次事务的多事件会导致误触发。仅从明确成功的业务入口提交展示请求。

当前确认框先执行业务回调再关闭，UIManager 又有入栈/出栈动画。需要在确认框实际关闭后展示奖励；关闭详情浮层并等待上一个弹窗完成退出，避免面板互相关闭或盖住奖励。

## C：升级、升阶及技能反馈

### 普通升级：短、清楚、可连续操作

- 约 0.4–0.6 秒：等级轻弹，数字由真实旧值滚到新值；仅变化的属性短暂高亮，显示一次 `+3`、`+5%` 等增量。
- 人物圆台/脚底出现小范围光圈，升级按钮轻压反馈；不每次打开独立大弹窗。
- 攻击、生命、防御使用整数；移速、倍率、百分比保持原有精度与单位。显示与差值来自数值模型，不能解析拼好的文本再计算。
- 满级/资源不足时给明确状态，不播放成功动效、不多扣资源。

### 升阶：突出阶段跨越

- 约 0.8–1.2 秒：短蓄光 → 阶级徽章或标记提升 → 人物亮起 → 新能力揭晓。
- 若本次解锁了专属能力，显示真实技能名、图标与关键效果；锁标淡出，节点点亮，关联文字依次出现。
- 玩家可跳过揭晓；快速操作需单次事务锁，不因多次点击重复消耗碎片。
- 未解锁技能保持可读，区别“当前阶段锁定”与“刚刚解锁”，不能仅用同一灰色刷新代替揭晓。

### 先修刷新生命周期，再加动画

当前升级/升阶会发布 PlayerDataChanged，HomeHubController 随之刷新当前页签，角色面板又重建卡牌和属性行。直接在行上加动画会被随后的重建销毁。

建议在成功操作入口捕获同一角色的 before/after 快照，复用属性行实例并进行增量绑定，再触发一次反馈。货币和红点照常刷新；动画期间合并重复的角色内容刷新。切换角色/页签、关闭或失焦时取消动画，立刻落到最终正确数值，重新打开不重播过去的升级。

`CharacterPanelPresentation.Refresh` 只负责静态最终状态，另设 `PlayLevelUp` / `PlayTierUnlock` 表现入口，避免每次刷新都误播解锁。

这里先按角色养成面板的属性与专属技能解锁规划。若“技能面板”同时包括局内技能选卡，再增加同一技能图标脉冲、等级跳字、突破标记点亮；沿用已有选卡流程，避免再加第二层奖励弹窗。

## 共用资源与验收

资源建议放在 `Assets/Res/image/Home/common/feedback/` 和 `Assets/Res/image/Game/role/` 的对应角色子目录，使用英文命名。优先复用当前按钮、面板、图标、字体和通用粒子。新增少量分件/小光效，不能仅凭源 PNG 大小推断微信构建包增长。

每阶段保留独立前后对比短视频，并记录同一微信构建设置下的资源/代码包增量。先用一个角色和一次完整领取闭环通过验收，再扩展接入。

- 角色：八方向移动、跨左右边界瞄准、近身目标切换、攻击/受击叠加、暂停恢复、重开、五角色切换；真实枪口与弹道方向一致。
- 奖励：免费/广告/货币兑换、单件/多件、快速双击、广告失败/重复回调、连续领取排队、领取中关闭、重开；资源只变化一次。
- 成长：升级成功/失败/满级，属性格式正确，连续升级，切页/切角色，升阶解锁与无解锁分支；最终 UI 和存档完全一致。
- 性能：战斗同屏怪物多时无新增逐帧全场查找；相同关卡与机型比较帧时间/内存，确认包体后再决定 Spine 或分帧的扩展预算。
