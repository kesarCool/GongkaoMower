## 三、iOS CPU 问题诊断结论

### 已尝试的优化（本轮，无效）

| 改动 | 预期 | 实际 |
|------|------|------|
| Physics2DSettings 迭代次数 8→4 | 降低物理 CPU | 🔴 已还原，可能是恶化原因 |
| WordMonsterShatterRuntime 去 Rigidbody2D | 省 64 个物理体 | 碎片不是常态，收益微弱 |
| PlayerController 合并 FindNearest | 省 O(N) 扫描 | 忽略不计 |
| EnemyAI/EnemyBase 缓存 GetComponent | 省层级查找 | 忽略不计 |

### 根因

**WebGL 1.0 + iOS JSC 无 JIT**，WASM 纯解释执行。C# 脚本层优化无法改变这个底层约束。

当前配置：
- `Webgl2: 0` — 软件渲染，像素走 CPU
- `enableEmscriptenGLX: 0` — 未开启
- `enableiOSMetal: 0` — 未开启

### 可行的下一步

| 方向 | 风险 | 预期收益 |
|------|------|---------|
| 开 WebGL 2.0 | 未知兼容问题 | 渲染搬 GPU，CPU 降 30-50% |
| `Time.fixedDeltaTime` 1/30 → 1/20 | 物理手感微变 | 物理仿真频率降 1/3 |
| `IOSDevicePixelRatio` 设 0.5 | 画面模糊 | 像素填充量减半 |

> **建议**：等审核结果出来再决定是否继续投 iOS 性能。如果 Dev Build 能过审，iOS 性能不是提审阻断项。

## 四、P1-5 经济系统改造：钻石 + 碎片分层

### 是否可以开工？

✅ **可以。** 经济系统改造是纯游戏逻辑 + 配表，不影响 v1.1.10 提审包。注意事项：
- 在开发分支做，别污染当前提审分支
- 核心玩法通顺以后再合并，防止审核没过需要回滚

### 改造方案

```
首通 → 钻石 + 碎片（确定性，一次性）
重复刷 → 金币（日常消耗）
商店 → 钻石兑换碎片（限购，每日/每周刷新）
困难模式 → 额外碎片掉落（概率，吸引重复刷）
```

三条线独立可控：

| 产出线 | 通货 | 用途 | 调控手段 |
|--------|------|------|------|
| 首通 | 钻石 | 商店买碎片 | 每关给多少钻石 |
| 商店 | 碎片 | 升星 | 限购次数 + 价格 |
| 困难 | 碎片 | 补缺口 | 掉落概率 |

### 具体改动（待实现）

- [ ] `PlayerSaveData` 已有 `diamond` 字段，确认 `AddDiamond`/`SpendDiamond` 可用
- [ ] `BattleOutcomeCoordinator` 首通结算给钻石（首次通关 +N 钻石）
