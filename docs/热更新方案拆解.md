# 热更新方案拆解（面试备考）

> 简历里出现了 YooAsset、HybridCLR、差分更新，拆开讲清楚每层是干什么的、为什么要搭配用。

---

## 一、先理解一个根本问题：为什么需要热更新

**App Store / 应用商店审核周期长**（1-3 天），游戏出 Bug 或要上新活动，等审核太慢。

热更新的目标：**绕过应用商店审核，直接向玩家推送代码和资源更新**。

但这有个技术限制——苹果/安卓的规则：

| 能绕过审核更新的 | 不能绕过、必须审核的 |
|---|---|
| 资源文件（图片、音效、预制体、场景） | 原生可执行代码（arm64 .so / .dll） |
| 脚本代码（前提：不是 AOT 编译进 native 的） | App 本身的二进制 |

所以热更新的核心问题就变成了：**怎么让 C# 代码不被 AOT 编译进 native，而是可以动态加载？**

## 二、Unity 方案：YooAsset + HybridCLR

### 2.1 先分开看：各管什么

```
┌─────────────────────────────────────────────┐
│                Unity 热更新架构               │
│                                             │
│   ┌──────────────┐   ┌──────────────┐       │
│   │  HybridCLR   │   │   YooAsset   │       │
│   │  负责：代码   │   │   负责：资源  │       │
│   ├──────────────┤   ├──────────────┤       │
│   │ 加载 C# DLL  │   │ 管理 AssetBundle │    │
│   │ 解释执行 IL  │   │ 版本比对 + 下载 │    │
│   │ 绕过 AOT     │   │ 加载 + 卸载    │    │
│   └──────────────┘   └──────────────┘       │
│          ↓                   ↓              │
│    更新游戏逻辑         更新图片/模型/音效    │
└─────────────────────────────────────────────┘
```

### 2.2 HybridCLR：让 C# 代码可以热更新

**为什么 Unity 的 C# 代码默认不能热更？**

```
普通 Unity IL2CPP 编译流程：
  C# 源码 → IL 中间码 → C++ 源码 → 编译成原生机器码 (arm64 .so)
                                    ↑
                          这一步已经写死进 APK/IPA
                          改一行 C# 就要重新出包 + 审核
```

IL2CPP 是 **AOT（Ahead-of-Time，预编译）**——所有代码在打包时就编译成机器码了，运行时没有解释器，根本无法加载新的 C# 代码。

**HybridCLR 做了什么？**

```
HybridCLR 流程：
  C# 源码 → IL 中间码 → 打包成 .dll 文件 → 放 AssetBundle 里（当普通资源）
                              ↓
              运行时：HybridCLR 解释器加载这个 DLL
              按需把 IL 指令翻译成机器码执行
                              ↓
              热更新：下载新 DLL → 替换旧的 → 重载
```

HybridCLR 本质上是给 IL2CPP 环境补了一个 **解释器**——AOT 时代码已经编译了，但额外提供一个能力：加载外部 DLL 并用解释方式执行其中的代码。

**为什么必须用它？**

- Unity WebGL / iOS 只能走 IL2CPP，没有 Mono（JIT）选项
- IL2CPP 的 AOT 模式天然不支持动态加载代码
- HybridCLR 是唯一能在 IL2CPP 下实现 C# 热更的方案

### 2.3 AssetBundle 基础——YooAsset 的底层积木

YooAsset 再花哨，底层管的是 AssetBundle。先搞懂 AB 本身怎么用。

**AssetBundle 是什么**：把一堆 Unity 资源（Prefab、贴图、材质、音效、场景……）打包成一个 `.bundle` 文件——可以放在远端，运行时按需下载和加载。

```
打包前：100 张散图 PNG + 50 个 Prefab + 20 个音效 → 散落在 Assets/ 各处
打包后：ui.bundle（UI 图集 + 字体）、characters.bundle（角色 Prefab + 动画）、audio.bundle（音效）
       → 三个文件，放在 CDN 上，运行时按需下载
```

**核心理解：不是"加载文件"，是"加载文件里的 Asset"**

AssetBundle 是一个容器，里面装了很多 Asset。加载时先加载容器，再从容器里取东西：

```
AssetBundle "ui.bundle"
  ├─ ui_atlas.png（一整张图）
  ├─ button_bg（Sprite —— 从 ui_atlas 里切出来的一个精灵）
  ├─ panel_bg（Sprite）
  ├─ Panel_Shop（Prefab —— 里面引用了 button_bg 和 panel_bg）
  └─ Panel_Bag（Prefab）
```

**从头到尾操作 AssetBundle 的完整流程**：

```
① 设置 Asset Labels（Editor 内）
   选中资源 → Inspector 底部 → Asset Labels → 给资源打标签
   例如：所有 UI 图片打 "ui" 标签、所有角色 Prefab 打 "characters" 标签

② 构建 AssetBundle（Build）
   Unity Editor → Window → AssetBundle Browser
   或脚本：BuildPipeline.BuildAssetBundles(outputDir, ...)
   → 输出目录生成一堆 .bundle 文件 + 一个总的 manifest 文件

③ 上传到 CDN / 放进 StreamingAssets
   构建产物 → 传到 CDN（或 App 打包时放进 StreamingAssets）

④ 运行时加载
   三种加载方式：
   
   方式 A：从文件加载（本地路径）
   AssetBundle ab = AssetBundle.LoadFromFile(path);
   
   方式 B：从内存加载（已下载的 byte[]）
   AssetBundle ab = AssetBundle.LoadFromMemory(bytes);
   
   方式 C：异步加载（不卡主线程）
   AssetBundleCreateRequest request = AssetBundle.LoadFromFileAsync(path);
   yield return request;
   AssetBundle ab = request.assetBundle;

⑤ 从 AssetBundle 里取 Asset
   // 取 Prefab
   GameObject prefab = ab.LoadAsset<GameObject>("Panel_Shop");
   // 实例化
   Instantiate(prefab);
   
   // 取 Sprite
   Sprite icon = ab.LoadAsset<Sprite>("button_bg");
   
   // 取所有 Asset（批量）
   Object[] all = ab.LoadAllAssets();

⑥ 用完了卸载
   AssetBundle.Unload(false);  // 卸掉 AB 自身，但保留已经从 AB 实例化到场景里的对象
   AssetBundle.Unload(true);   // 卸掉 AB + 连带销毁场景里所有从这个 AB 来的实例
```

**依赖关系是 AssetBundle 最大的坑**：

```
Panel_Shop.prefab 在 ui.bundle 里
  但它引用的 ui_atlas.png 在 common.bundle 里
    → 加载 Panel_Shop 之前，必须先加载 common.bundle
    → 否则贴图丢失，Prefab 上只有紫色方块

Unity 的 manifest 文件记录了这些依赖：
  ui.bundle 依赖 → common.bundle
  所以加载 ui.bundle 之前，先加载它所依赖的所有 Bundle
```

**manifest 文件的作用**：

```
构建时 Unity 自动生成一个总的 .manifest 文件（文本，可读）：

ManifestFileVersion: 0
AssetBundleManifest:                    ← 记录所有 AB 之间的依赖关系
  ui.bundle:
    - common.bundle                     ← ui.bundle 依赖 common
  characters.bundle:
    - common.bundle                     ← characters.bundle 也依赖 common
  common.bundle: []                     ← common 不依赖别人

运行时：
  1. 先加载总 manifest
  2. 要加载 ui.bundle → 查 manifest → 依赖 common.bundle → 先加载 common → 再加载 ui
```

**常见坑**：

| 坑 | 现象 | 原因 | 解法 |
|---|---|---|---|
| 重复打包 | 同一个贴图出现在多个 Bundle 里 → 包体膨胀 | 两个 AB 都引用了同一张贴图 | 公共资源抽到 common.bundle，其他 Bundle 不直接引用 |
| 依赖缺失 | 场景里出现紫色方块 | 加载了 Prefab 所在 AB 但没加载它依赖的 AB | 先查 manifest 加载所有依赖，再加载目标 AB |
| 内存泄漏 | 越玩越卡，内存一直涨 | `LoadAsset` 之后从不用 `Unload` | 切场景时 `Unload(false)` 清理已加载的 AB |
| Unload(true) 误杀 | 场景里某 Prefab 的贴图突然全变紫 | Unload(true) 把还在用的实例也一起销毁了 | 确认 Asset 没有任何场景引用后才用 `Unload(true)` |

**这整套手动流程，YooAsset 全帮你做了**——所以下一节开始讲的三种模式和资源管理机制，本质上就是把上面这些 Load/Unload/Dependency/Manifest 操作封装了起来。

### 2.4 YooAsset：三种运行模式

YooAsset 不是只有一个"下载→加载"的笼统概念，它有三套运行模式，分别对应开发、测试、生产三个环境。

**模式选型表**：

| 模式 | 资源从哪来 | 需要构建 AssetBundle？ | 适用 |
|---|---|---|---|
| **编辑器模拟模式** | 直接用项目里的 Asset | ❌ 不需要 | 本地开发、快速迭代 |
| **离线模式** | App 内置的 AssetBundle | ✅ 需要 | 无热更需求、或首包就打全资源 |
| **联机模式** | CDN 远端下载 | ✅ 需要 | 正式上线、有热更需求 |

**编辑器模拟模式（Editor Simulate Mode）**：

开发阶段不想每次改个 Sprite 就重新打 AssetBundle → 配成模拟模式 → YooAsset 直接从 `Assets/` 目录加载原始资源 → 跟正式模式 API 完全一样 → 开发效率拉满。

```csharp
// 同一个 API，模拟模式和联机模式一样用
var handle = package.LoadAssetAsync<Sprite>("ui_icon_coin");
handle.Completed += (h) => {
    coinIcon.sprite = h.AssetObject as Sprite;
};
```

**离线模式（Offline Play Mode）**：

App 安装时就带好所有 AssetBundle（放 StreamingAssets 里），不走 CDN。适合无热更需求的单机游戏，或者首包资源。加载时 YooAsset 从本地文件系统读。

**联机模式（Host Play Mode）**：

App 装好只带最小首包 → 启动时 YooAsset 去 CDN 拉 manifest → 比对本地版本 → 有差异就下载 → 下载完从本地缓存加载。

这三种模式只在配置文件里切一行代码，业务层无感知——这就是 YooAsset 设计上比手写 AssetBundle 好的核心原因。

### 2.5 YooAsset：资源管理机制

#### 2.4.1 核心概念：Package（资源包）

YooAsset 的资源组织围绕一个核心概念——**Package**。一个 Package 对应一组资源，有自己的 manifest、自己的版本号、自己的下载管线。

```
Package "Default"
├── manifest (版本号 + 所有 AssetBundle 的 hash 列表)
├── AssetBundle A: ui_atlas.bundle (1.2MB, md5: a1b2...)
├── AssetBundle B: characters.bundle (5.3MB, md5: c3d4...)
├── AssetBundle C: effects.bundle (2.1MB, md5: e5f6...)
└── ...

典型分法：
  Default → 共用资源（UI、字体、音效）
  Battle  → 战斗场景独有
  Home    → 大厅场景独有
```

**为什么按场景拆 Package？**

不是所有玩家都会玩到所有内容。一个新玩家进游戏，只需要 Default + Home 的包就能进大厅。等他匹配进战斗了，才去下载 Battle 包。不玩的永远不下——省流量、省首包时间。

#### 2.4.2 版本管理全流程

```
① 开发者构建：
   打 AssetBundle → 生成 manifest（记录每个 Bundle 的 hash + 版本号）
   → 上传到 CDN

② 玩家启动：
   YooAsset.Initialize(package, mode=联机模式, cdnUrl=...)
   → 去 CDN 拉最新 manifest

③ 比对版本：
   CDN manifest.version vs 本地 cache 里的 manifest.version
   一样 → 跳过下载，直接加载
   不一样 → 进入④

④ 逐文件比对（类似 Cocos 差分逻辑）：
   遍历 CDN manifest 里每个 AssetBundle:
     - 本地不存在 → 下载
     - 本地 hash ≠ CDN hash → 下载（文件变了）
     - 本地 hash == CDN hash → 跳过（没变）

⑤ 下载：
   并发下载变更文件 → 每个下载完校验 md5 → 写入本地缓存

⑥ 加载：
   资源句柄 → package.LoadAssetAsync<T>(path)
   → YooAsset 从本地缓存读取 → 引用计数 +1
```

**关键：跟 Cocos 差分更新的对比**

| | YooAsset | Cocos 差分 |
|---|---|---|
| 更新粒度 | AssetBundle（一组资源） | 单文件（每个 .js / .png） |
| hash 算法 | MD5 / CRC | MD5 |
| 并发下载 | 内置，支持断点续传 | 需自建或第三方 |
| 资源加载 | `LoadAssetAsync<T>` 强类型 | `cc.resources.load` 回调/异步 |
| 卸载 | 引用计数 + 手动 Release | JS GC 自动回收（不可控） |

#### 2.4.3 加载与卸载：引用计数机制

这是 YooAsset 跟手写 AssetBundle 最核心的区别之一——**不是你 Load 了就不用管，也不是你不敢 Unload 怕别人还在用**。

```csharp
// 加载
var handle = package.LoadAssetAsync<GameObject>("Enemy_Boss");
handle.Completed += (h) => {
    var boss = Instantiate(h.AssetObject as GameObject);
    // AssetBoss.bundle 引用计数 +1
};

// 用完了
package.Release(handle);
// Enemy_Boss.bundle 引用计数 -1
// 如果降到 0 → YooAsset 自动 Dispose，连带卸载所有无人使用的依赖
```

**引用计数的设计意义**：

场景切换时，旧场景的资源如果不手动卸载 → 内存泄漏。手写 AssetBundle 管理的项目经常出现「内存越玩越大」——就是忘了 Unload。YooAsset 每个 Load 有对应 Release，内部记着计数，配合 `UnloadUnusedAssets` 可以安全地清理。

#### 2.4.4 缓存策略

```
本地缓存目录：
  persistentDataPath/
  └── YooAsset/
      └── Default/
          ├── cache_manifest.json         ← 本地 manifest
          ├── a1b2c3d4...bundle           ← 以 hash 命名的缓存文件
          ├── c3d4e5f6...bundle
          └── ...
```

- 下载完的 Bundle 保留供下次启动用
- 缓存有上限（可配置，如 500MB），超限时 LRU 淘汰最久未用的
- `ClearUnusedCacheFilesAsync()` 清掉 manifest 里不再引用的旧文件

### 2.6 为什么 YooAsset + HybridCLR 要一起用

**因为它们解决的是两个不同维度的问题，缺一不可：**

| 场景 | 只用 YooAsset | 只用 HybridCLR | 两个一起 |
|---|---|---|---|
| 换一张活动图 | ✅ 能做到 | ❌ 资源不受它管 | ✅ |
| 修一个战斗 Bug | ❌ 改不了代码 | ✅ 可以加载新 DLL | ✅ |
| 上线一个新技能 | ❌ 需要新代码 | ✅ | ✅ |
| 完整活动更新 | ❌ | ❌（缺资源） | ✅ |

**实际协作流程：**

```
1. 开发提交 C# 代码 + 新资源
2. 构建脚本：
   - C# 代码 → 编译成 DLL → HybridCLR 热更包
   - 资源 → 打成 AssetBundle → YooAsset 管理
3. 两者一起上传到 CDN
4. 玩家启动游戏：
   - YooAsset 检查资源版本 → 下载新 AssetBundle
   - HybridCLR 从 AssetBundle 里提取 DLL → 加载执行
5. 重载完成，新逻辑 + 新资源同时生效
```

### 2.7 面试怎么讲（30 秒版本）

> Unity 的 IL2CPP 是 AOT 编译，代码写死进原生二进制，不能热更。HybridCLR 给 IL2CPP 补了一个解释器，让 C# 编译成的 DLL 可以像资源一样放在 AssetBundle 里动态加载执行。YooAsset 负责管理 AssetBundle 的版本比对、下载、加载、卸载。两者配合：HybridCLR 管代码更新，YooAsset 管资源更新，合在一起实现完整的热更新闭环。

## 三、Cocos Creator 方案：差分更新

### 3.1 为什么 Cocos 不需要 HybridCLR 这种东西

Cocos Creator 用的是 **JavaScript / TypeScript**，JS 天生就是解释执行的——不存在「AOT 编译写死」的问题。脚本文件就是 `.js` 文本，替换掉就生效。

**Cocos 热更新的核心问题跟 Unity 完全不同**：不是「怎么执行新代码」，而是「怎么高效地把改过的文件从服务器拉到手机上」。

**Cocos 热更新在原生和 Web 上都支持，但底层不一样**：

| 平台 | JS 引擎 | 文件存储 | 热更文件放哪 |
|---|---|---|---|
| **原生（iOS/Android）** | JSB（JS Binding，V8 引擎） | 有文件系统写权限 | `jsb.fileUtils.getWritablePath()` → App 沙盒目录 |
| **Web / H5** | 浏览器 JS 引擎 | ❌ 无持久文件写权限 | 内存缓存 / IndexedDB / ServiceWorker，或直接重新请求新文件 |
| **微信小游戏** | 微信 JS Runtime | 有（`wx.env.USER_DATA_PATH`） | 微信沙盒目录 |

所以流程上原生和 Web 都能走 manifest 比对——区别只在第三步"下载完写到哪里"。Web 平台的限制是**无法像原生一样把文件写到文件系统然后后续启动时读**，所以 Web 上的热更新一般退化为「判断有更新 → 提示用户刷新页面」，或者用 Service Worker 做缓存拦截。

### 3.2 AssetsManager：确实自带对比机制

Cocos Creator 内置了热更新管理器，不需要自己写比对逻辑：

| Cocos 版本 | 热更模块 |
|---|---|
| **Cocos 2.x** | `cc.AssetsManager` / `AssetsManagerEx`——独立的热更新类，负责整个流程 |
| **Cocos 3.x** | 整合进 `assetManager`，通过 `bundle` 的热更新接口实现 |

**AssetsManager 内部做的事**：

```
AssetsManager 内部流程：
  ① 设置远端 manifest URL
  ② 调用 checkUpdate()
     → 下载远端 project.manifest
     → 读取本地 project.manifest
     → 内部逐文件比对 hash     ← 自带的，不用你写
     → 返回需要下载的文件列表
  ③ 调用 update()
     → 并发下载变更文件
     → 每个下载完校验 md5
     → 写入本地存储
     → 更新本地 manifest
  ④ 下次 cc.game.restart() → 读本地已更新的文件
```

**所以"直接对比 manifest 就行"是对的——但这个对比不是手动写的，是 AssetsManager 内部做的**。你只需要：

```javascript
// Cocos 2.x 用法
let am = new cc.AssetsManager(remoteManifestUrl, localStoragePath);
am.checkUpdate((error, hasUpdate, newManifest) => {
    if (hasUpdate) {
        am.update((error, failedList) => {
            if (!error) {
                cc.game.restart(); // 重启以加载新文件
            }
        });
    }
});
```

### 3.3 差分更新原理

**不是「整个 App 重新下载」，而是「只下载跟本地不一样的」：**

```
服务端                      客户端
  │                           │
  │  project.manifest         │  本地 project.manifest
  │  {                        │  {
  │    "version": "2.0",      │    "version": "1.0",
  │    "assets": {            │    "assets": {
  │      "main.js": "a1b2",   │      "main.js": "c3d4",   ← hash 不同
  │      "logo.png": "e5f6",  │      "logo.png": "e5f6",  ← hash 相同，跳过
  │      "bg.jpg": "g7h8",    │      // bg.jpg 不存在     ← 新增文件
  │    }                      │    }
  │  }                        │  }
  │                           │
  │                           ├─ 比对结果：
  │                           │   main.js: 下载（hash 变了）
  │                           │   bg.jpg: 下载（本地没有）
  │                           │   logo.png: 跳过（一样）
  │                           │
  │  ← 下载 main.js + bg.jpg  │
  │                           │
  │                           ├─ 写入本地存储
  │                           ├─ 标记 version = "2.0"
  │                           └─ 下次启动读新文件
```

**核心数据结构：manifest**

```json
{
  "packageUrl": "https://cdn.xxx.com/hotupdate/",
  "remoteManifestUrl": "https://cdn.xxx.com/hotupdate/project.manifest",
  "remoteVersionUrl": "https://cdn.xxx.com/hotupdate/version.manifest",
  "version": "2.0",
  "assets": {
    "src/main.js": {
      "md5": "a1b2c3d4..."
    },
    "res/logo.png": {
      "md5": "e5f6..."
    }
  }
}
```

**manifest 里的 hash 是什么——MD5 快速解释**

MD5 的作用就是给文件生成一个「指纹」。你把任何文件丢进 MD5 算法，它吐出一串 32 位的十六进制字符串：

```
logo.png (v1.0) → MD5: a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4
logo.png (v2.0) → MD5: 9x8y7z6a5b4c3d2e1f0a9b8c7d6e5f4   ← 只改了一个像素，结果完全不同
```

两个核心特性让它适合做文件比对：

1. **确定性**：同一个文件算出来的 MD5 永远一样
2. **雪崩效应**：文件哪怕只改了一个字节，MD5 结果天差地别

所以 manifest 里不需要存整个文件去比较，存 32 个字符的 MD5 就够了。比对的时候直接用字符串比较——一样就是同一份文件，跳过下载。

**为什么不用文件修改时间或文件体积来判断？**

- 文件修改时间不准（客户端时间可能被改、时区不对）
- 文件体积可能碰巧一样（两张不同的图恰好都是 100KB）
- 只有 hash 能做到「只要内容变了，指纹就一定不同」

**除了 MD5 还有哪些常见 hash 算法**

| 算法 | 输出长度 | 速度 | 碰撞风险 | 适用场景 |
|---|---|---|---|---|
| **MD5** | 128 bit（32 字符） | 快 | ⚠️ 已有碰撞攻击 | 文件完整性校验（非安全场景） |
| **SHA-1** | 160 bit（40 字符） | 中 | ⚠️ 已有碰撞攻击 | 曾用于 Git commit id，正在被淘汰 |
| **SHA-256** | 256 bit（64 字符） | 慢 | ✅ 目前安全 | 安全签名、证书、区块链 |
| **CRC32** | 32 bit（8 字符） | 极快 | ❌ 碰撞概率较高 | 网络传输校验（检测传输错误，不管恶意篡改） |
| **xxHash** | 32/64/128 bit | **极快**（比 MD5 快 10 倍+） | 低 | 游戏资源校验（Unity AssetBundle 内部用的就是 xxHash） |

**为什么差分更新通常选 MD5 而不是更安全的 SHA-256？**

差分更新的 hash 是用来「判断文件是否相同」，不是用来「防止恶意篡改」——这个场景不需要抗碰撞。MD5 比 SHA-256 快 3-5 倍，对一个有几千个文件的项目来说，速度差异是可感知的。反过来说，如果是要做数字签名、防篡改，就必须用 SHA-256。

**Unity AssetBundle 内部用的是 xxHash**——比 MD5 快一个数量级，适合游戏引擎在运行时高频校验资源完整性。你简历里写的「资源压缩加密」后半段如果要展开，也可以提这一点。

**版本比对三步走：**

```
Step 1: 比对版本号
  server.version > local.version? → 有更新，进入 Step 2
  server.version == local.version? → 无更新，跳过

Step 2: 逐文件比对 hash
  遍历 server.assets:
    - 本地不存在该文件 → 标记下载（新增）
    - 本地 hash != 服务端 hash → 标记下载（修改）
    - 本地 hash == 服务端 hash → 跳过（未变）
    - 服务端已删除本地还存在的文件 → 标记删除

Step 3: 批量下载
  把标记为下载的文件逐个拉下来 → 下载完再算一次 MD5 校验完整性 → 写入本地 → 更新本地 manifest
```

### 3.4 跟 Unity 方案的本质区别

| | Unity (YooAsset + HybridCLR) | Cocos Creator (差分) |
|---|---|---|
| 脚本语言 | C# | JavaScript / TypeScript |
| 代码热更方式 | 需要 HybridCLR 解释器 | 原生支持（JS 就是解释执行） |
| 资源热更方式 | YooAsset 管理 AssetBundle | 内置 AssetsManager，manifest 比对 |
| 更新粒度 | AssetBundle（一组资源打包） | 单文件（每个 .js / .png 独立比对） |
| 复杂度 | 高（两套系统配合） | 中（资源比对 + JS 替换，逻辑简单） |
| 为什么选 | Unity 被迫（IL2CPP 限制） | Cocos 天然优势 |

### 3.5 面试怎么讲（20 秒版本）

> Cocos Creator 用 JS，脚本本身就是解释执行，不需要像 Unity 那样补解释器。热更新核心是 manifest 差分比对——客户端拿本地 manifest 跟服务端逐文件对比 hash，只下载有变化的文件。版本号兜底，hash 完成为准，改了什么就下什么，不下全量包。

## 四、常见追问 & 回答建议

### Q1: HybridCLR 有性能损耗吗？

有，但项目里没感觉到。HybridCLR 的解释执行比 AOT 原生代码慢 3-5 倍。但游戏的热更代码主要是 UI 逻辑、活动规则、数据结算——这些不跑在热路径上。战斗热路径（碰撞检测、技能 Tick、物理）用的是 AOT 编译好的引擎代码，不经过 HybridCLR。

### Q2: AssetBundle 和 Resources 的区别？

`Resources` 所有资源打包进首包，App 安装时就占满，且不能热更新。`AssetBundle` 可以放在远端，按需下载，支持版本管理和增量更新。用了 YooAsset 后项目中基本不用 `Resources`，除了 FlatBuffers 数据表这种必须首包加载的基础配置。

### Q3: 分包跟热更新什么关系？

分包是**首包大小控制**，热更新是**后续内容更新**。微信小游戏首包有 4MB 限制，所以要把 WASM 代码和资源拆成子包，先让游戏启动起来，剩下的从 CDN 拉。YooAsset 可以同时管理分包策略和热更新策略。

### Q4: 差分更新失败怎么处理？

manifest 校验 + 回退。每个下载文件校验 md5，不通过就重试。如果整个版本更新失败（比如下载中断），保留旧版本 manifest，下次启动用旧版本进游戏，下次再试。不会出现「卡在更新界面进不去」的情况。

### Q5: 你做的文字割草机用了热更新吗？

没有。微信小游戏审核速度快（几小时），加之上线时是个人项目，没有对接 CDN 和热更新管线，直接走全量更新。但之前在中青宝负责的《守住那座塔》用 YooAsset + HybridCLR 实现了完整的热更新闭环，热更新响应效率提升了 60%。
