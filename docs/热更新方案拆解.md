# 热更新方案拆解（面试备考）

> 简历里出现了 YooAsset、HybridCLR、差分更新，拆开讲清楚每层是干什么的、为什么要搭配用。

---

## 一、先理解一个根本问题：为什么需要热更新

**App Store / 应用商店审核周期长**（1-3 天），游戏出 Bug 或要上新活动，等审核太慢。

热更新的目标：**绕过应用商店审核，直接向玩家推送代码和资源更新**。

但这有个技术限制——苹果/安卓的规则：

| 能绕过审核更新的 | 不能绕过、必须审核的 |
|---|---|
| 资源文件（图片、音效、预制体、场景） | 原生可执行代码（arm64 .so / .dll） |
| 脚本代码（前提：不是 AOT 编译进 native 的） | App 本身的二进制 |

所以热更新的核心问题就变成了：**怎么让 C# 代码不被 AOT 编译进 native，而是可以动态加载？**

---

## 二、Unity 方案：YooAsset + HybridCLR

### 2.1 先分开看：各管什么

```
┌─────────────────────────────────────────────┐
│                Unity 热更新架构               │
│                                             │
│   ┌──────────────┐   ┌──────────────┐       │
│   │  HybridCLR   │   │   YooAsset   │       │
│   │  负责：代码   │   │   负责：资源  │       │
│   ├──────────────┤   ├──────────────┤       │
│   │ 加载 C# DLL  │   │ 管理 AssetBundle │    │
│   │ 解释执行 IL  │   │ 版本比对 + 下载 │    │
│   │ 绕过 AOT     │   │ 加载 + 卸载    │    │
│   └──────────────┘   └──────────────┘       │
│          ↓                   ↓              │
│    更新游戏逻辑         更新图片/模型/音效    │
└─────────────────────────────────────────────┘
```

### 2.2 HybridCLR：让 C# 代码可以热更新

**为什么 Unity 的 C# 代码默认不能热更？**

```
普通 Unity IL2CPP 编译流程：
  C# 源码 → IL 中间码 → C++ 源码 → 编译成原生机器码 (arm64 .so)
                                    ↑
                          这一步已经写死进 APK/IPA
                          改一行 C# 就要重新出包 + 审核
```

IL2CPP 是 **AOT（Ahead-of-Time，预编译）**——所有代码在打包时就编译成机器码了，运行时没有解释器，根本无法加载新的 C# 代码。

**HybridCLR 做了什么？**

```
HybridCLR 流程：
  C# 源码 → IL 中间码 → 打包成 .dll 文件 → 放 AssetBundle 里（当普通资源）
                              ↓
              运行时：HybridCLR 解释器加载这个 DLL
              按需把 IL 指令翻译成机器码执行
                              ↓
              热更新：下载新 DLL → 替换旧的 → 重载
```

HybridCLR 本质上是给 IL2CPP 环境补了一个 **解释器**——AOT 时代码已经编译了，但额外提供一个能力：加载外部 DLL 并用解释方式执行其中的代码。

**为什么必须用它？**

- Unity WebGL / iOS 只能走 IL2CPP，没有 Mono（JIT）选项
- IL2CPP 的 AOT 模式天然不支持动态加载代码
- HybridCLR 是唯一能在 IL2CPP 下实现 C# 热更的方案

### 2.3 YooAsset：让资源可以热更新

**Unity 原生资源管理的问题：**

| 原生方案 | 问题 |
|---|---|
| `Resources` 文件夹 | 所有资源打进首包，无法热更；加载慢 |
| `AssetBundle` 手动管理 | 需要自己写加载/卸载/依赖/版本比对逻辑 |
| `Addressables` | Unity 官方方案，但版本比对手游太重，灵活性不够 |

**YooAsset 解决的：**

```
资源更新流程：
  启动 → 检查远端 manifest → 比对本地版本
    → 有更新 → 下载变动文件 → 校验 → 写入本地
    → 没更新 → 直接读本地缓存
    → 加载资源（支持异步/同步，引用计数，自动卸载）
```

### 2.4 为什么 YooAsset + HybridCLR 要一起用

**因为它们解决的是两个不同维度的问题，缺一不可：**

| 场景 | 只用 YooAsset | 只用 HybridCLR | 两个一起 |
|---|---|---|---|
| 换一张活动图 | ✅ 能做到 | ❌ 资源不受它管 | ✅ |
| 修一个战斗 Bug | ❌ 改不了代码 | ✅ 可以加载新 DLL | ✅ |
| 上线一个新技能 | ❌ 需要新代码 | ✅ | ✅ |
| 完整活动更新 | ❌ | ❌（缺资源） | ✅ |

**实际协作流程：**

```
1. 开发提交 C# 代码 + 新资源
2. 构建脚本：
   - C# 代码 → 编译成 DLL → HybridCLR 热更包
   - 资源 → 打成 AssetBundle → YooAsset 管理
3. 两者一起上传到 CDN
4. 玩家启动游戏：
   - YooAsset 检查资源版本 → 下载新 AssetBundle
   - HybridCLR 从 AssetBundle 里提取 DLL → 加载执行
5. 重载完成，新逻辑 + 新资源同时生效
```

### 2.5 面试怎么讲（30 秒版本）

> Unity 的 IL2CPP 是 AOT 编译，代码写死进原生二进制，不能热更。HybridCLR 给 IL2CPP 补了一个解释器，让 C# 编译成的 DLL 可以像资源一样放在 AssetBundle 里动态加载执行。YooAsset 负责管理 AssetBundle 的版本比对、下载、加载、卸载。两者配合：HybridCLR 管代码更新，YooAsset 管资源更新，合在一起实现完整的热更新闭环。

## 三、Cocos Creator 方案：差分更新

### 3.1 为什么 Cocos 不需要 HybridCLR 这种东西

Cocos Creator 用的是 **JavaScript / TypeScript**，JS 天生就是解释执行的——不存在「AOT 编译写死」的问题。脚本文件就是 `.js` 文本，替换掉就生效。

**Cocos 热更新的核心问题跟 Unity 完全不同**：不是「怎么执行新代码」，而是「怎么高效地把改过的文件从服务器拉到手机上」。

### 3.2 差分更新原理

**不是「整个 App 重新下载」，而是「只下载跟本地不一样的」：**

```
服务端                      客户端
  │                           │
  │  project.manifest         │  本地 project.manifest
  │  {                        │  {
  │    "version": "2.0",      │    "version": "1.0",
  │    "assets": {            │    "assets": {
  │      "main.js": "a1b2",   │      "main.js": "c3d4",   ← hash 不同
  │      "logo.png": "e5f6",  │      "logo.png": "e5f6",  ← hash 相同，跳过
  │      "bg.jpg": "g7h8",    │      // bg.jpg 不存在     ← 新增文件
  │    }                      │    }
  │  }                        │  }
  │                           │
  │                           ├─ 比对结果：
  │                           │   main.js: 下载（hash 变了）
  │                           │   bg.jpg: 下载（本地没有）
  │                           │   logo.png: 跳过（一样）
  │                           │
  │  ← 下载 main.js + bg.jpg  │
  │                           │
  │                           ├─ 写入本地存储
  │                           ├─ 标记 version = "2.0"
  │                           └─ 下次启动读新文件
```

**核心数据结构：manifest**

```json
{
  "packageUrl": "https://cdn.xxx.com/hotupdate/",
  "remoteManifestUrl": "https://cdn.xxx.com/hotupdate/project.manifest",
  "remoteVersionUrl": "https://cdn.xxx.com/hotupdate/version.manifest",
  "version": "2.0",
  "assets": {
    "src/main.js": {
      "md5": "a1b2c3d4..."
    },
    "res/logo.png": {
      "md5": "e5f6..."
    }
  }
}
```

**manifest 里的 hash 是什么——MD5 快速解释**

MD5 的作用就是给文件生成一个「指纹」。你把任何文件丢进 MD5 算法，它吐出一串 32 位的十六进制字符串：

```
logo.png (v1.0) → MD5: a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4
logo.png (v2.0) → MD5: 9x8y7z6a5b4c3d2e1f0a9b8c7d6e5f4   ← 只改了一个像素，结果完全不同
```

两个核心特性让它适合做文件比对：

1. **确定性**：同一个文件算出来的 MD5 永远一样
2. **雪崩效应**：文件哪怕只改了一个字节，MD5 结果天差地别

所以 manifest 里不需要存整个文件去比较，存 32 个字符的 MD5 就够了。比对的时候直接用字符串比较——一样就是同一份文件，跳过下载。

**为什么不用文件修改时间或文件体积来判断？**

- 文件修改时间不准（客户端时间可能被改、时区不对）
- 文件体积可能碰巧一样（两张不同的图恰好都是 100KB）
- 只有 hash 能做到「只要内容变了，指纹就一定不同」

**除了 MD5 还有哪些常见 hash 算法**

| 算法 | 输出长度 | 速度 | 碰撞风险 | 适用场景 |
|---|---|---|---|---|
| **MD5** | 128 bit（32 字符） | 快 | ⚠️ 已有碰撞攻击 | 文件完整性校验（非安全场景） |
| **SHA-1** | 160 bit（40 字符） | 中 | ⚠️ 已有碰撞攻击 | 曾用于 Git commit id，正在被淘汰 |
| **SHA-256** | 256 bit（64 字符） | 慢 | ✅ 目前安全 | 安全签名、证书、区块链 |
| **CRC32** | 32 bit（8 字符） | 极快 | ❌ 碰撞概率较高 | 网络传输校验（检测传输错误，不管恶意篡改） |
| **xxHash** | 32/64/128 bit | **极快**（比 MD5 快 10 倍+） | 低 | 游戏资源校验（Unity AssetBundle 内部用的就是 xxHash） |

**为什么差分更新通常选 MD5 而不是更安全的 SHA-256？**

差分更新的 hash 是用来「判断文件是否相同」，不是用来「防止恶意篡改」——这个场景不需要抗碰撞。MD5 比 SHA-256 快 3-5 倍，对一个有几千个文件的项目来说，速度差异是可感知的。反过来说，如果是要做数字签名、防篡改，就必须用 SHA-256。

**Unity AssetBundle 内部用的是 xxHash**——比 MD5 快一个数量级，适合游戏引擎在运行时高频校验资源完整性。你简历里写的「资源压缩加密」后半段如果要展开，也可以提这一点。

**版本比对三步走：**

```
Step 1: 比对版本号
  server.version > local.version? → 有更新，进入 Step 2
  server.version == local.version? → 无更新，跳过

Step 2: 逐文件比对 hash
  遍历 server.assets:
    - 本地不存在该文件 → 标记下载（新增）
    - 本地 hash != 服务端 hash → 标记下载（修改）
    - 本地 hash == 服务端 hash → 跳过（未变）
    - 服务端已删除本地还存在的文件 → 标记删除

Step 3: 批量下载
  把标记为下载的文件逐个拉下来 → 下载完再算一次 MD5 校验完整性 → 写入本地 → 更新本地 manifest
```

### 3.3 跟 Unity 方案的本质区别

| | Unity (YooAsset + HybridCLR) | Cocos Creator (差分) |
|---|---|---|
| 脚本语言 | C# | JavaScript / TypeScript |
| 代码热更方式 | 需要 HybridCLR 解释器 | 原生支持（JS 就是解释执行） |
| 资源热更方式 | YooAsset 管理 AssetBundle | 内置 AssetsManager，manifest 比对 |
| 更新粒度 | AssetBundle（一组资源打包） | 单文件（每个 .js / .png 独立比对） |
| 复杂度 | 高（两套系统配合） | 中（资源比对 + JS 替换，逻辑简单） |
| 为什么选 | Unity 被迫（IL2CPP 限制） | Cocos 天然优势 |

### 3.4 面试怎么讲（20 秒版本）

> Cocos Creator 用 JS，脚本本身就是解释执行，不需要像 Unity 那样补解释器。热更新核心是 manifest 差分比对——客户端拿本地 manifest 跟服务端逐文件对比 hash，只下载有变化的文件。版本号兜底，hash 完成为准，改了什么就下什么，不下全量包。

## 四、常见追问 & 回答建议

### Q1: HybridCLR 有性能损耗吗？

有，但项目里没感觉到。HybridCLR 的解释执行比 AOT 原生代码慢 3-5 倍。但游戏的热更代码主要是 UI 逻辑、活动规则、数据结算——这些不跑在热路径上。战斗热路径（碰撞检测、技能 Tick、物理）用的是 AOT 编译好的引擎代码，不经过 HybridCLR。

### Q2: AssetBundle 和 Resources 的区别？

`Resources` 所有资源打包进首包，App 安装时就占满，且不能热更新。`AssetBundle` 可以放在远端，按需下载，支持版本管理和增量更新。用了 YooAsset 后项目中基本不用 `Resources`，除了 FlatBuffers 数据表这种必须首包加载的基础配置。

### Q3: 分包跟热更新什么关系？

分包是**首包大小控制**，热更新是**后续内容更新**。微信小游戏首包有 4MB 限制，所以要把 WASM 代码和资源拆成子包，先让游戏启动起来，剩下的从 CDN 拉。YooAsset 可以同时管理分包策略和热更新策略。

### Q4: 差分更新失败怎么处理？

manifest 校验 + 回退。每个下载文件校验 md5，不通过就重试。如果整个版本更新失败（比如下载中断），保留旧版本 manifest，下次启动用旧版本进游戏，下次再试。不会出现「卡在更新界面进不去」的情况。

### Q5: 你做的文字割草机用了热更新吗？

没有。微信小游戏审核速度快（几小时），加之上线时是个人项目，没有对接 CDN 和热更新管线，直接走全量更新。但之前在中青宝负责的《守住那座塔》用 YooAsset + HybridCLR 实现了完整的热更新闭环，热更新响应效率提升了 60%。
