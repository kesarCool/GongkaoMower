## Q8：HTTP 与长连接（TCP / WebSocket）的区别

**面试官在考什么**：知不知道不同协议的性能模型和适用场景，能不能为具体需求做正确选型。

**标准答案**：

| | HTTP 短连接 | TCP 长连接 | WebSocket |
|---|---|---|---|
| 连接方式 | 请求→响应→断开 | 持久连接，一直不断 | 基于 TCP 的全双工协议 |
| 谁主动 | 客户端主动请求，服务端被动响应 | 都可以主动发 | **服务端可以主动推** |
| 协议头大小 | 大（几百字节 headers） | 自定义，能做到几字节 | 2-14 字节 |
| 延迟 | 高（握手 + 头开销） | 低 | 低 |
| 适用 | 登录、存档、活动数据 | 实时战斗、MOBA 帧同步 | 聊天、大厅通知、排行榜推送 |

**为什么 HTTP 不适合实时战斗**：

```
HTTP 请求一次：
  客户端发起 → TCP 三次握手(如果连接池没复用) → 发请求头+体 → 等服务端处理 → 接收响应头+体
  → 全程 ~50-200ms，其中 HTTP Header 就占 200-500 字节

帧同步一帧：
  客户端发操作指令 → 服务端收集所有人 → 广播 → 客户端执行
  → 全程必须 < 50ms，数据量只有几十字节（按键/坐标）
  
用 HTTP 来做 → 一帧的 Header 开销是实际数据的 10 倍 → 王者荣耀一局至少几千帧 → 光 HTTP 头就浪费 MB 级流量
```

**TCP 长连接的核心是"连接复用"**：

```
TCP 三次握手 + TLS 四次握手 → 连接建立
  → 每帧发一包数据（不用再握手）
  → 连接一直开着
  → 心跳包维持（闲置太久会被路由器/NAT 掐断）
  → 游戏结束 → 四次挥手断开
```

**8 年该怎么说**：

> 做《御剑三国》的时候，世界聊天服一开始用 HTTP 轮询——每 5 秒 GET 一次消息列表。用户量上去了之后，1000 人在线每人每 5 秒一次请求 → 服务器扛不住。后来全部改成 WebSocket 长连接——服务端有新消息主动推给在线用户，不用轮询。从 HTTP 轮询改到 WebSocket Push 之后，聊天服 CPU 降了 70%，消息延迟从 5 秒最坏情况变成了毫秒级。

## Q9：WebSocket 用法 + 心跳与断线重连

**面试官在考什么**：知不知道 WebSocket 不是说连上就万事大吉——中间路由器/NAT 会掐断闲置连接，必须有心跳。知不知道断线重连怎么做。

**标准答案**：

**WebSocket 基本用法（Cocos 2.x）**：

```typescript
let ws = new WebSocket("wss://game.xxx.com:8080");

ws.onopen = () => {
    // 连上了，开始发登录包
    ws.send(JSON.stringify({ type: "login", token: "xxx" }));
};

ws.onmessage = (event) => {
    let msg = JSON.parse(event.data);
    // 分发消息
};

ws.onerror = (event) => { /* 错误处理 */ };
ws.onclose = (event) => { /* 开始重连逻辑 */ };
```

**心跳机制**：

```
为什么需要心跳：
  WebSocket 连接本身是长连接，但不发数据时被中间路由器/NAT 设备判定为"死连接"
  → 路由器/NAT 有超时机制（通常 1-5 分钟）
  → 超时后掐断 → 客户端和服务端都不知道连接已死 → 直到下次发消息才发现
  → 就丢了中间这段时间的消息

心跳协议约定：
  客户端每 30 秒发 → { type: "ping" }
  服务端收到后回 → { type: "pong" }
  客户端超时（比如 15 秒没收到 pong）→ 判定连接断裂 → 开始重连
```

```typescript
class WebSocketWithHeartbeat {
    private ws: WebSocket;
    private heartbeatInterval = 30000;   // 30 秒发一次
    private heartbeatTimeout = 15000;    // 15 秒没收回复 → 判定断开
    private _timer: number;

    private startHeartbeat() {
        this._timer = setInterval(() => {
            if (this.ws.readyState === WebSocket.OPEN) {
                this.ws.send(JSON.stringify({ type: "ping" }));
                // 设置超时检测
                setTimeout(() => {
                    // 15 秒后还没收到 pong → 主动断开重连
                    if (this.ws.readyState === WebSocket.OPEN) {
                        this.ws.close();
                    }
                }, this.heartbeatTimeout);
            }
        }, this.heartbeatInterval);
    }
}
```

**断线重连的完整状态机**：

```
状态机：
  Connected → 心跳超时 → Disconnected → 等待 N 秒 → Reconnecting
    → 重连成功 → Connected
    → 重连失败 → 等待 2N 秒 → Reconnecting（指数退避）
    → 重试 5 次仍失败 → 弹出"网络断开，请检查网络"

退避策略：
  第 1 次重试：等 1 秒
  第 2 次重试：等 2 秒
  第 3 次重试：等 4 秒
  第 4 次重试：等 8 秒
  第 5 次重试：等 16 秒（总共 ~31 秒）→ 放弃，提示用户
```

**重连期间的玩家体验**：

断线时不能直接把玩家踢了——要先显示"重连中…"遮罩，让游戏世界保持暂停状态（但不是客户端暂停，是服务端记下玩家最后状态）。重连成功后服务端补推断线期间的状态变更。

**8 年该怎么说**：

> 在《御剑三国》里做过多人在线战斗的重连模块。最开始的方案是断线就踢回大厅——玩家体验极差。后来改成了 30 秒心跳 + 断线 5 秒自动重连 + 重连期间战斗暂停（渲染层遮罩"重连中"，逻辑层服务端等 10 秒超时）。重连成功后服务端一次性下推断线期间的战斗日志，客户端快播到当前状态。10 秒没重连回来才判定离线。

> 另外发现一个容易被忽略的问题——后台切回来。iOS 把 App 切后台会冻结 WebSocket，切回来的时候 Socket 可能已经半死了。所以要监听浏览器的 `visibilitychange` 事件：切前台后主动发一个 ping，看不到 pong 就马上重连。

## Q10：TCP 粘包 / 拆包及解决方案

**面试官在考什么**：TCP 是字节流，不是消息流。知不知道"发两次"不一定是"收两次"——以及怎么在应用层封出正确的消息边界。

**标准答案**：

**粘包/拆包是什么**：

```
服务端连发三个包：
  发包1: [AAAAAAAA]
  发包2: [BBBB]
  发包3: [CCCCCC]

客户端可能收到：
  情况一（正常）：[AAAAAAAA] [BBBB] [CCCCCC]
  情况二（粘包）：[AAAAAAAABBBBCCCCCC]  三个包粘成一个
  情况三（拆包）：[AAAA] [AAAABBBBCC] [CCCC]  被拆成意料之外的片段
```

**为什么 TCP 会这样**：TCP 是字节流协议，它只保证字节按顺序、不丢、不重复地送达——不关心哪里是"一条消息的开始和结束"。Nagle 算法（积攒小包）和接收缓冲区的大小决定了具体怎么粘/拆。

**三种解决方案**：

| 方案 | 原理 | 适用 |
|---|---|---|
| **定长包** | 每个消息固定 N 字节，不够用 0 填充 | 简单但浪费带宽 |
| **分隔符** | 每条消息末尾加 `\r\n` 等特殊分隔符 | 文本协议（HTTP 就用这招） |
| **包头 + 包体（最常用）** | 固定 4 字节头 = 包体长度 + 后面跟包体数据 | 二进制协议，性能最好 |

**"包头 + 包体"的具体实现**：

```
协议格式：
  [4 字节：包体长度 N] [N 字节：包体数据]
  例如：0x00 0x00 0x00 0x0A  [H][e][l][l][o][ ][W][o][r][l][d]
         ↑ 包体长 = 10          ↑ 10 字节的包体

解码逻辑：
  缓冲区：...收到的零散字节往里塞...
  
  while (缓冲区长度 >= 4) {
      N = 读前 4 字节;  // 包体长度
      if (缓冲区长度 < 4 + N) break;  // 还没收完，等更多字节
      
      包体 = 读接下来的 N 字节;
      处理完整消息(包体);
      从缓冲区删掉 4+N 字节;
  }
```

**ProtoBuf 配合粘包处理**：

ProtoBuf 本身不处理粘包——它只管序列化。通常开发者会在 ProtoBuf 字节流前面加上 2-4 字节的长度头，形成自描述的消息帧。

**8 年该怎么说**：

> 在《御剑三国》的帧同步战斗里，每帧服务器广播的操作数据量都很小——几十字节。不用帧头的话，Nagle 算法会把好几帧的操作数据攒在一起发，客户端收到后拿 ProtoBuf 反序列化只能解出第一条，后面全是乱码。加上 2 字节的包头长度字段之后，解码器先读长度再读数据，粘包了就循环解，拆包了就等缓冲区够长再解。这套方案上线后没再出过粘包 Bug。

## Q11：ProtoBuf 和 JSON 怎么选

**面试官在考什么**：知不知道 ProtoBuf 优势在哪，劣势在哪，不同场景该用谁。

> 详细答案见 [面试高频追问.md](面试高频追问.md) 第三章，覆盖了体积对比、Schema 校验、版本兼容、性能数据、游戏为什么选 ProtoBuf。

**补充点（Cocos / JS 环境特有）**：

在 Cocos Creator 项目里，ProtoBuf 的缺点比 Unity 环境下更明显。因为 Cocos 没有 IL2CPP 的反射坑——JS 天生就适合 JSON。用 ProtoBuf 要额外引入 `protobufjs` 库 + 维护 `.proto` 文件 + 每次改协议要重新生成 JS 代码。所以 Cocos 项目用 ProtoBuf 一定是因为**对包体大小和性能有硬需求**（比如实时帧同步每帧几十个包），否则 JSON 完全够用。

**8 年该怎么说**：

> 在《御剑三国》里同时用了两种——登录、大厅、商店这种一次性请求用 JSON，调试方便、前端单独开发时可以 mock。实时战斗帧同步用 ProtoBuf——每帧几十字节的操作数据走 JSON 的话包体会从 ~30 字节变成 ~120 字节，一局游戏几千帧，差距就是几百 KB vs 几十 KB。

## Q12：帧同步 vs 状态同步

**面试官在考什么**：知不知道两种同步模型的原理、优缺点、适用场景——以及在自己项目里为什么选这个。

> 同步模型基础见 [面试高频追问.md](面试高频追问.md) 五-B 章。这里补充深入对比。

**核心差异一张表**：

| | 帧同步（Lockstep） | 状态同步（State Sync） |
|---|---|---|
| **谁算** | 每个客户端各自算（确定性逻辑） | 服务端算完下发结果 |
| **传什么** | 玩家操作指令（按键/坐标） | 游戏状态（位置/血量/技能CD） |
| **带宽** | 极小（几十字节/帧） | 中到大（取决于状态量） |
| **延迟** | "等最慢的人"→ 一个人卡全房间卡 | 不等 → 每个人看到的是服务端"过去"的 |
| **防作弊** | 弱（客户端自己算，可以改） | 强（服务端是权威） |
| **重连难度** | 需要追赶几百帧 | 拉一次快照就行 |
| **确定性要求** | **极高**——浮点计算必须完全一致 | 低——服务端算好就行 |
| **代表游戏** | 王者荣耀、LOL、War3 | MMORPG、吃鸡、原神 |

**为什么 SLG 通常走状态同步**

SLG 不是实时动作游戏——几秒甚至几分钟延迟不致命。状态同步天然适合：服务端算好战斗结果 → 下发给客户端 → 客户端只需要精确回放。安全方面也是加分——氪金游戏服务端必须是权威。

**8 年该怎么说**：

> 《御剑三国》的战斗虽然是即时观战模式，但核心决策在服务端——玩家配置部队→下令攻击→服务端跑战斗逻辑→下推结果给所有观战者。本质上是一个状态同步架构，跟 MOBA 的帧同步完全两个路线。选这个方案的核心原因是 SLG 对公平性（防作弊）和重连体验的要求比延迟更重要——玩家可以接受等 2 秒看到战斗结果，不能接受有人改客户端的数据。

## Q13：延迟下保证手感：客户端预测与服务器和解

**面试官在考什么**：知不知道在状态同步模式下，客户端不能干等服务端回复——要做本地预测，然后跟服务端"和解"。这是 FPS/ACT 网络架构的进阶话题。

**问题**：

```
状态同步下：
  玩家按下"移动" → 客户端发请求给服务端 → 服务端处理 → 回复新位置 → 客户端更新画面
  → 全程 ~50-200ms 往返
  → 玩家感觉按了键但人物过了 0.2 秒才有反应 → 手感极其差
```

**客户端预测**：

```
客户端不等服务端回复：
  按下移动 → 客户端立即移动人物（预测服务端会同意） → 同时发请求
  → 服务端 50ms 后回复 → 对比预测位置和权威位置
    → 一致 → 什么都不做 ✅
    → 不一致 → 把人物拉回到服务端位置（和解 Reconciliation）
```

**服务器和解**：

```
服务端收到请求时标记时间戳 → 服务端处理 → 回复时带上"我处理的是时间 T 的输入"

客户端维护一个未确认的输入队列：
  [{ time: T0, input: "move_right" }, { time: T1, input: "attack" }]

收到服务端回复 "已处理到 T0"：
  → 从队列里删掉时间 ≤ T0 的输入
  → 如果服务端说"你这个 move_right 我判了但位置跟你的预测差了一点"
    → 把人物拉到服务端说的位置
    → 把 T0 之后队列里还没确认的输入重新在服务端位置的基础上播放一遍
```

**SLG 里不需要这个**

SLG 不是实时动作游戏，不需要客户端预测和解和——这是 FPS/ACT 的进阶技巧。但面试官问到意味着在考你对网络同步的理解深度。

**8 年该怎么说**：

> 客户端预测和和解我了解原理，在《御剑三国》这个 SLG 项目上没用，因为 SLG 不要求毫秒级操作反馈。但如果是做实时动作游戏，这是必须的——客户端预测解决操作延迟，服务端和解解决不一致。核心思路是客户端不等服务端，先自己跑了再说，服务端回复了再纠正；纠正的时候不是直接跳到服务端位置（会跳帧），而是做平滑插值拉过去。
