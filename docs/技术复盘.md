## 二、详细复盘

### 2.1 非 Dev Build 下游戏启动卡死 ⭐

**现象**

`DevelopBuild: 1` 时打包和加载正常。设为 `0` 后，打包成功，但微信开发者工具加载时报错：

```
[PLUGIN ERROR] 加载资源异常 Cannot read property 'createDataFile' of undefined
[PLUGIN ERROR] start game fail: TypeError: Cannot read property 'createDataFile' of undefined
[PLUGIN ERROR] still waiting runDependencies, ids= ["wasm-preloadAssets"]
```

游戏永远卡在启动封面。

**排查过程（8 轮）**

| 轮次 | 尝试 | 结果 |
|---|---|---|
| 1 | 怀疑微信开发者工具的调试面板是水印来源，尝试 `Debug.developerConsoleVisible = false` | ❌ 不相关 |
| 2 | 尝试用 Unity UI Canvas 遮挡水印 | ❌ 不可行 |
| 3 | Emscripten 优化级别降到 `-O1` | ❌ 直接 SyntaxError |
| 4 | `BuildOptions.AllowDebugging` | ❌ 与 `-O1` 同类问题 |
| 5 | Proxy 拦截 `Module` 属性，尝试给 Plugin 注入 FS | ❌ 确认 Plugin 完全不经过 Module |
| 6 | 替换 `Module.processRawData` | ❌ Plugin 用的是内部引用，不走 Module |
| 7 | 手动调用 SDK 的 `unityFileSystemInit` | ❌ `createDataFile` 未出现 |
| 8 | **dump Plugin 源码**（`toString()` 输出闭包内 `processRawData`） | ✅ **找到根因** |

**根因**

微信 UnityPlugin v1.2.91 的 `processRawData` 函数在闭包内引用了模块级变量 `f`：

```javascript
// Plugin 闭包内（简化）
var f;
// ... 
function processRawData(r) {
    f.FS.createPath(...);
    f.FS.createDataFile(r, null, s.slice(t, t+n), !0, !0, !0);
}
```

`f.FS` 依赖 WX SDK 的 ReplaceRules（~38 条正则）在 Unity 输出的 framework JS 中注入 FS 替换层。

- **Dev Build**：framework JS 不压缩，变量名保留原样，38 条正则全部匹配成功 → `f.FS` 正确挂载
- **非 Dev Build**：Unity/Emscripten 压缩了 JS，变量名被混淆，38 条正则全部匹配失败 → `f.FS = undefined`

关键死结：`f` 在 Plugin 闭包内，`processRawData` 被 Plugin 内部引用调用。外部代码既不能写入 `f`，也不能拦截 `processRawData`，所有从外部注入的尝试都绕不过闭包隔离。

**结论**

在当前环境下不可修复。保持 `DevelopBuild: 1`，接受右下角 `development build` 水印。

**可能的出路**（未验证）：
1. 升级 Unity 到 2022.2+：`Application.debugMode` API 可在非 Dev Build 下关水印
2. 升级微信 UnityPlugin：若新版本修复了闭包设计
3. 切换到团结引擎（Tuanjie）：微信官方推荐，原生 WeixinMiniGame 构建目标

**学到什么**

- 排查第三方 SDK 问题时，`toString()` dump 闭包源码是最后的手段，但也是最有效的手段
- 在依赖链复杂时（Unity → Emscripten → WX SDK → UnityPlugin），先画完整链路再动手，避免头疼医头
- 正则替换这种"靠文本匹配做代码注入"的方案本质上很脆弱。变量名一变就全挂，这是设计层面上的问题，不是调参数能解决的
- 借助 AI（Claude Code）辅助阅读 minified JS、推理闭包作用域、设计诊断步骤，大幅缩短了排查时间。第 5-8 轮的方案设计基本靠 AI 辅助 brainstorm 出来的

### 2.2 游戏内主动分享无法拉起

**现象**

游戏内按钮点击调用 `WXShareHelper.ShareForRevive()` → 微信分享面板不弹出。日志显示 C#→JS 调用链完整走到 JS 层，但 `wx.shareAppMessage()` 就是不触发。

**排查**

发现三层问题逐层叠加：

| 层 | 问题 | 详情 |
|---|---|---|
| ① 桥函数缺失 | `WX_OneWayNoFunction_vt` 未编译进 wasm | IL2CPP 裁剪掉了 SDK DLL 需要但未被直接引用的桥函数 |
| ② 手势上下文 | `wx.shareAppMessage()` 必须在微信原生 touch 回调中同步调用 | C# EventSystem → jslib → JS 的链路已经丢失了原始 touch 事件的上下文 |
| ③ Plugin 拦截 | WX UnityPlugin 在 capture 阶段消费 touch | JS 层的 `wx.onTouchEnd` 可能根本收不到事件 |

层②和层③的连锁效应：

```
微信 Touch → [Plugin 在 capture 阶段拦截] → Unity Input → C# EventSystem
                                                   ↓
                                              jslib → JS → wx.shareAppMessage ❌（上下文丢失）
微信 Touch → [Plugin 拦截了] → JS wx.onTouchEnd ❌（事件被消费，到不了 JS 层）
```

层①可修（手动补 jslib 桩），但层②和层③都是架构层面的限制。

**解决**

放弃主动分享。改用**被动分享**：在 `share.js` 中注册 `wx.onShareAppMessage`，利用微信右上角「…」菜单的转发入口，这个路径不走 C# 事件链，正常工作。

**学到什么**

- 微信小游戏的敏感 API（分享、支付、广告）都有「必须在用户手势回调中同步调用」的限制，这是反滥用机制。跨语言调用链（C# → JS）天然与这个机制冲突
- 立项阶段就应该验证这些平台限制，而不是做到一半才发现——这个教训值钱
- 主动分享需求如果要实现，可能需要微信 UnityPlugin 层面支持，把 touch 事件在 Plugin 内部直接转发给分享 API，不经过 C# 层

### 2.3 IL2CPP 反射裁剪导致数据表加载失败

**现象**

切换到 IL2CPP + WebGL 构建后，游戏启动时 `TableManager` 加载 FlatBuffers 数据表失败，报 `MissingMethodException: __init`。

**排查**

FlatBuffers 的原始 `TableManager` 实现用 C# 反射来初始化每个表类型：

```csharp
var method = type.GetMethod("__init");
method.Invoke(obj, new object[] { 0, bb });  // ← IL2CPP 不认识这个字符串引用
```

IL2CPP 在编译时做静态代码分析来确定哪些方法需要保留。`GetMethod("__init")` 是字符串参数，IL2CPP 看不到「这个方法被引用了」→ 裁剪掉 `__init` → 运行时找不到方法。

**解决**

不走反射，所有 FlatBuffers 表类型都实现了 `IFlatbufferObject` 接口，转型后直接调用：

```csharp
var obj = (IFlatbufferObject)Activator.CreateInstance(type);
obj.__init(0, bb);  // ← IL2CPP 看到接口引用，不会裁
```

**学到什么**

- IL2CPP + 反射 = 基本会出事。Unity 的 Managed Stripping 等级越高（WebGL 默认 High），越容易踩这个坑
- 遇到 IL2CPP 找不到方法的错误，第一反应应该是「是不是被裁了」，然后检查调用方式是不是用了字符串形式的方法名
- 解决方案的核心思路不是「关闭裁剪」（会增大包体），而是「让 IL2CPP 的静态分析能看到引用」——用接口、用 `[Preserve]` 注解、用 `link.xml`

### 2.4 TMP 中文字体渲染

**问题**

微信环境下 TextMeshPro 默认字体（LiberationSans SDF）不含汉字，所有中文显示为方块或空白。

**方案探索**

| 方案 | 结果 |
|---|---|
| `WX.GetWxFont()` 获取微信系统字体 | 开发者工具有效，**真机环境行为不一致**，废弃 |
| Unity 自带的 Fallback Font | 只对 `Text` 组件有效，TMP 不支持 |
| 制作中文字体 SDF Asset | ✅ 最终方案 |

**最终方案**

使用微软雅黑制作 SDF 字体文件（`msyh SDF.asset`），覆盖 7000+ 常用汉字：
- 字体文件 7.2MB，放 `Resources/Fonts/`
- Prefab 上 TMP 组件用轻量 LiberationSans 占位，避免大字体被打进首包引用
- 运行时由 `BattleChineseFontRuntime` 统一替换：
  - 经 `UIManager.Open<T>()` 打开的弹窗 → `ApplyToHierarchy` 批量替换子树
  - 局内文字怪 `EnemyWordLabel` → `TryApplyTo` 单独替换
  - 动态创建或不经 UIManager 的 TMP → `TMPChineseFontAutoApply` 组件兜底

**学到什么**

- 微信小游戏的字体方案比原生 App 受限得多。微信系统字体 API 在开发者工具和真机上表现不一致，不能依赖
- SDF 字体文件很大（7MB），必须有意识地控制引用链，避免 Prefab 直接引用导致被打进首包
- 「占位 + 运行时替换」是这个场景下性价比最高的模式

### 2.5 WASM 分包超 4MB 限制

**问题**

首次构建时 WASM 代码包超过微信小游戏的 4MB 单包限制，上传审核被拒。

**解决**

三个配置组合解决：

| 配置 | 作用 | 效果 |
|---|---|---|
| `ScriptOnly: 1` | WASM 代码拆分为独立分包 | 代码不进首包 |
| `compressDataPackage: 1` | Brotli 压缩数据包 | 17MB → br 压缩 |
| `assetLoadType: 1` | 资源放小游戏分包（非 CDN） | 无需额外 CDN 部署 |

最终包体结构：
- 首包 ~650 KB（JS 框架）
- wasmcode 分包 5.1 MB（br 压缩后）
- data-package 分包 17 MB（br 压缩后）

**学到什么**

- 微信小游戏的包体限制不是建议，是硬性门槛。立项时就要评估资源量，别做好了才发现塞不进
- Brotli 压缩对 Unity 资源（纹理、字体、场景数据）效果显著
- `ScriptOnly` 分包是 WX SDK 提供的功能，不是 Unity 原生能力——构建管线比想象的多一层

### 2.6 场景切换后单例数据丢失

**问题**

从 Home 场景切换到 Game 场景后，`MonoSingleton` 子类（如 `TableManager`）的数据被重置。

**原因**

Unity 默认 `SceneManager.LoadScene` 会销毁旧场景所有 GameObject，包括挂载了 `MonoSingleton` 的根物体。

**解决**

`MonoSingleton` 的 `Awake` 中加 `DontDestroyOnLoad(gameObject)`：

```csharp
protected virtual void Awake()
{
    if (Instance != null && Instance != this)
    {
        Destroy(gameObject);
        return;
    }
    Instance = this;
    DontDestroyOnLoad(gameObject);  // ← 场景切换时不销毁
}
```

**学到什么**

- Unity 单例模式的坑在场景切换时才暴露。编辑器里只跑一个场景看不出问题
- `Destroy(gameObject)` 后 `Instance` 仍指向已销毁对象的引用 → 后续访问会抛 `MissingReferenceException`。赋值 `Instance = this` 前必须先判空

### 2.7 NPOI DLL 被打进 WebGL 构建

**问题**

项目引用了 NPOI（Excel 读取库），用于编辑器工具读取 Excel。但在 IL2CPP WebGL 构建时，NPOI 的 DLL 被打进了构建产物，增加了不必要的包体积。

**原因**

NPOI 的 `.dll.meta` 中平台设置是所有平台启用。

**解决**

将 NPOI 相关 `.dll.meta` 中 `WebGL: enabled: 0`，只在 Editor 平台启用：

```
Assets/Plugins/NPOI/*.meta → platformData: WebGL → enabled: 0
```

**学到什么**

- Unity 的 Plugin Inspector 里每个 DLL 可以按平台设置启用/禁用。这个设置在 `.meta` 文件里
- 编辑器工具依赖的第三方库很容易被忘记排除，构建后检查包体内容是个好习惯

### 2.8 WX SDK V1→V2 升级后 jslib 缺失

**问题**

从 WX-WASM-SDK V1 升级到 V2 后，WebGL 构建报错：多个 JS 函数未注册（`WX_OneWayNoFunction_vt`、`WXGetFontRawData`、`WXShareFontBuffer` 等），WASM 加载失败。

**原因**

V2 版本的 C# DLL 依赖了几个新的 jslib 桥接函数，但对应的 jslib 文件没有随 SDK 一起分发，或者版本不匹配。

**解决**

创建桩文件 `SDK-WX-Bridge-Fix.jslib`，补充缺失的 JS 函数桩：

```javascript
mergeInto(LibraryManager.library, {
    SetUnityUIType: function() {},
    WXHideLoadingPage: function() {},
    WXGetFontRawData: function() { return 0; },
    WXShareFontBuffer: function() {},
    // ... 其他缺失函数
});
```

后续为分享功能新增了 `SetShareImageIds` 桥接。

**学到什么**

- SDK 版本升级后一定要全量验证构建，不能假设「之前能跑现在就能跑」
- jslib 是 Unity WebGL 中 C# 调用 JS 的桥接机制（`[DllImport("__Internal")]`），函数签名必须在编译时注册
- 桩函数不等于功能实现——`WXGetFontRawData` 返回 0 只是防止 WASM abort，真正的字体能力需要另起方案

### 2.9 UI Text 全量迁移到 TextMeshPro

**问题**

微信 WebGL 环境下，Unity 原生 `Text` 组件的中文渲染效果很差（模糊、缺字），且不受 SDF 字体控制。

**解决**

编写编辑器工具 `ConvertTextToTMP.cs`，菜单：**Tools → 批量转换 Text 到 TMP**，自动将场景和 Prefab 中的 `UnityEngine.UI.Text` 转换为 `TextMeshProUGUI`，保留文字内容、颜色、字号、对齐方式。

**学到什么**

- 这类批量转换工具是「一次性写好、反复使用」的典型场景。手动替换几十个 Text 组件既慢又容易漏
- 转换工具要考虑保留原始属性（文字内容、颜色、字号、对齐、Rich Text 开关），否则转换完还得逐个检查

### 2.10 性能优化：从卡顿到流畅运行

微信小游戏是基于 WebGL/WASM 的，WASM 堆大小默认 256MB（Emscripten `TOTAL_MEMORY` 编译参数）。虽不是微信官方的硬性限制，但在低端机上可用的总内存确实有限，同屏数百敌人 + 大量弹丸 + 粒子特效的场景下，不做优化帧率会掉到个位数。

#### 2.10.1 降帧率：60 → 30 FPS

这是性价比最高的单步优化——直接砍掉一半的渲染和逻辑压力。

```csharp
// AppBootstrap.Awake()
QualitySettings.vSyncCount = 1;
#if !UNITY_WEBGL || UNITY_EDITOR
    Application.targetFrameRate = 30;           // Editor/Standalone
#else
    WeChatWASM.WX.SetPreferredFramesPerSecond(30); // 微信 WebGL
#endif
Time.fixedDeltaTime = 1f / 30f;                 // 物理步长同步
Time.maximumDeltaTime = 1f / 15f;               // 防死亡螺旋（卡一帧不会雪崩）
```

**分平台处理的原因**：微信 WebGL 环境下，`Application.targetFrameRate` 和 `QualitySettings.vSyncCount` 都无效——帧率由浏览器/微信 runtime 控制。必须通过 WX SDK 的 `.jslib` 桥直接调用微信 `wx.setPreferredFramesPerSecond` API。

`Time.maximumDeltaTime = 1f / 15f` 的作用：当某一帧卡了 200ms，Unity 不会试图在下一帧「追回」这些时间（导致更严重的卡顿），而是把 deltaTime 截断到 1/15 秒。

#### 2.10.2 分帧生成（SpawnLimiter）

**问题**：波次开始时瞬间生成几十只怪物 → 单帧 Instantiate/Active 尖峰 → 明显卡顿。

**方案**：`SpawnLimiter` 按类型管控生成速率。

```
SpawnLimiter 结构：
  ├─ maxAlive: 该类型同时存活上限（如 Enemy=100）
  ├─ spawnPerFrame: 每帧最多生成数（如 Enemy=5）
  ├─ recycleOldest: 超限时是否回收最旧对象
  └─ LateUpdate: 每帧重置 spawnThisFrame 计数器
```

`SpawnerWaves` 协程中检查限制：

```csharp
// 当本帧已达生成上限 → yield return null 跳到下一帧
if (!SpawnLimiter.Instance.CanSpawn("Enemy", out var cfg))
{
    if (cfg.spawnPerFrame > 0)
    {
        yield return null;  // 让出这一帧
        i--;                // 重新尝试本次生成
        continue;
    }
    break;  // 全局达到上限，停止生成
}
```

#### 2.10.3 怪物对象池 + 预加载

**对象池**（`GameObjectPool`）：

- 按 Prefab 分池，每池独立 Stack + maxInactive 上限
- 借出登记 `LeasedObjects`（HashSet）→ `ClearAllPools` 时精确清理，不做全场景扫描
- 回池时若超过 `maxInactive` 上限直接 Destroy，防止池无限膨胀
- 离局（Game 场景卸载）自动 `ClearAllPools`

**预加载**（`PoolPrewarmOnStart`）：

- Inspector 配置要预热的 Prefab + 数量
- `Awake` 时批量 `GameObjectPool.Prewarm(prefab, count)` → 提前 Instantiate 并 SetActive(false)
- 运行时 `Get` 直接从池里取 inactive 对象，SetActive(true) 几乎零开销

**效果**：原本每次生成怪物都要 `Instantiate`（几十到几百 ms 尖峰），预加载后首次取用 < 1ms。

#### 2.10.4 死亡碎片分帧释放（WordMonsterShatterRuntime）

**问题**：清屏时几十只怪物同时死亡 → 每只碎裂出 4 个字 → 瞬间 100+ `new GameObject` + `TextMeshPro` 初始化 → 严重卡顿。

**方案**：全局预算 + 分帧消化队列。

```
控制参数：
  maxActiveFragments = 64       // 全局同时存在上限
  digestSpreadFrames = 4        // 分摊到 N 帧消化
  → MaxNewFragmentsPerFrame = 64 / 4 = 16  // 每帧最多新增
  maxPendingFragments = 2048    // 待生成队列上限（防极端泄漏）
```

- 怪物死亡不直接生成碎片，而是快照 TMP 数据 → 入队 `_pending`
- 单例 `Update` 每帧按 cap 从队列取、生成、加入 `_activeFragments`
- 碎片统一 Tick（纯 Transform 运动，无 Rigidbody2D、无独立 MonoBehaviour.Update）
- 队列超 2048 时自动丢最旧的（极端防御，正常不会触发）

**性能对比**：
- 优化前：50 只怪同时死亡 → 单帧 200+ `new GameObject` → 卡顿 200-500ms
- 优化后：分摊到 ~13 帧 → 每帧 16 个 → 帧率无明显波动

#### 2.10.5 同屏怪物上限 + 旧对象回收

`SpawnLimiter` 的 `maxAlive` + `recycleOldest` 组合：

```
maxAlive = 100 (同屏最多 100 只)
recycleOldest = true (超限时回收最旧的，为新怪腾位置)

逻辑：
  新怪要生成 → 检查 currentAlive >= maxAlive?
    → 否：正常生成
    → 是 + recycleOldest：Dequeue 最旧怪物 → Release 回池 → 生成新怪
    → 是 + 不回收：拒绝生成（SpawnerWaves 跳过本次）
```

**为什么是回收最旧而非随机**：最旧的怪物通常离玩家最远（出生时间早，追人时间短），杀它对玩家体验影响最小；同时避免新老怪物交替时出现的闪烁感。

#### 2.10.6 全局索敌注册表替代 FindObjectsWithTag

先解释一个概念——**GC（Garbage Collection，垃圾回收）**跟 CPU/GPU 是不同的东西：

| | 职责 | 出问题时表现 |
|---|---|---|
| **CPU** | 每帧算多少东西（逻辑、物理） | 帧率持续偏低 |
| **GPU** | 每帧画多少像素（渲染） | 画面撕裂、掉帧 |
| **GC** | 回收不再使用的堆内存 | **间歇性猛卡**（回收时所有线程暂停） |

GC 的问题不在「持续慢」，而在**尖峰**。对于 30 FPS 的游戏，每帧预算只有 ~33ms。GC 触发一次通常耗时 50-100ms，相当于直接丢 2-3 帧——玩家感知就是一瞬的卡顿。

这个项目里 GC 压力的主要来源之一就是 `FindGameObjectsWithTag`：每次调用都会在堆上分配一个新的 `GameObject[]` 数组，用完即弃。同屏 100 敌、6 个技能都在索敌的极端场景下，每秒可能触发多次 GC。

**方案**：`CombatTargetRegistry` 替代 `FindGameObjectsWithTag`。

核心设计是一个静态的 `Dictionary<string, List<Transform>>`，按 Tag 分桶：

```
Buckets = {
  "monster" → [EnemyA.transform, EnemyB.transform, EnemyC.transform, ...]
  "Player"  → [Player.transform]
}
```

**注册/注销（OnEnable/OnDisable）**：

怪物 Prefab 上的 `EnemyBase` 组件在 `OnEnable` 时调用 `CombatTargetRegistry.Register(gameObject)`，把自己加入对应 Tag 的列表；`OnDisable` 时调用 `Unregister` 移除。对象池借出/归还、死亡 Disable 都会自动触发进出——零维护成本。

**查询时惰性清理**：

不在 Update 里定时清理（会产生额外遍历），而是在每次查询时边遍历边剔除失效条目：

```csharp
for (int i = list.Count - 1; i >= 0; i--)
{
    if (!IsAlive(list[i]))       // null 或未激活 → 已被池回收/销毁
    {
        RemoveAt(list, i);       // 用列表末尾元素补位，O(1) 删除
        continue;
    }
    // 正常匹配逻辑...
}
```

`RemoveAt` 用的是 swap-with-last 技巧——把最后一个元素移到当前位置，然后 RemoveAt(last)——不需要移动中间所有元素，单次删除 O(1)：

```csharp
list[index] = list[last];
list.RemoveAt(last);
```

**为什么比 FindObjectsWithTag 快**：

| | FindObjectsWithTag | CombatTargetRegistry |
|---|---|---|
| 分配 | 每次分配新 `GameObject[]` | 零分配（只读已有 List） |
| 遍历范围 | 场景中 **所有** GameObject | 仅活跃敌人 |
| GC | 频繁触发 | 不触发 |
| 删除开销 | 不适用（每次重新分配） | O(1) swap-with-last |

同屏 100 敌时，每个技能的索敌查询从 ~0.5ms 降到 < 0.01ms，同时消除了 GC 尖峰。

#### 2.10.7 优化清单汇总

| 优化项 | 措施 | 效果 |
|---|---|---|
| 降帧率 | 60→30 FPS | 直接砍半 GPU/CPU 压力 |
| 分帧生成 | SpawnLimiter.spawnPerFrame | 消除波次开始时的生成尖峰 |
| 对象池 | GameObjectPool + 借出登记 | Instantiate 尖峰 → SetActive(true) |
| 怪物预加载 | PoolPrewarmOnStart | 首次取用 < 1ms |
| 死亡碎片分帧 | 全局 64 上限 + 4 帧消化 | 清屏不再卡顿 |
| 同屏上限 | maxAlive + FIFO 回收 | 内存和 CPU 可控 |
| 索敌注册表 | CombatTargetRegistry | 索敌 0.5ms → <0.01ms |
| 集中 Tick | 碎片无独立 Update | 省掉 N 个 MonoBehaviour 的开销 |

## 三、经验总结

### 3.1 流程层面

1. **平台限制提前验证**：微信分享、支付等敏感 API 有手势上下文要求，这类限制应该在立项阶段就用最小 Demo 验证，而不是功能做完了才发现不可行
2. **Dev Build 的取舍**：非 Dev Build 的问题根因是 SDK 设计缺陷，不是调参数能解决的。接受水印是当时性价比最高的选择，比死磕更务实
3. **SDK 版本升级要全量验证**：V1→V2 升级后出新的 jslib 缺失问题，说明 SDK 的升级路径不是平滑的

### 3.2 技术层面

1. **IL2CPP + 反射 = 定时炸弹**：WebGL 只能用 IL2CPP，而 IL2CPP 的代码裁剪对反射调用是盲的。用接口调用替代反射是成本最低的解法
2. **正则替换做代码注入很脆弱**：WX SDK 的 ReplaceRules 机制依赖变量名匹配，一旦 Emscripten 修改压缩策略就全挂。这种设计没有容错性
3. **字体方案要早定**：中文字体是微信小游戏的高频踩坑点，SDF + 运行时替换是经过验证的方案，但字体文件大小需要在首包引用链上做控制
4. **对象池和注册表是性能基座**：同屏数百敌人时，`FindObjectsWithTag` 的性能开销不可接受。`GameObjectPool` + `CombatTargetRegistry` 的设计把 GC 压力降到了可控范围

### 3.3 AI 工具的使用

整个开发周期中，Claude Code 和 Cursor 在以下场景提供了关键帮助：

- **Debug 诊断**：非 Dev Build 问题的第 5-8 轮诊断，dump 出的 minified JS 源码靠 AI 辅助阅读和理解闭包作用域
- **方案 brainstorm**：排查陷入死胡同时（如分享问题），AI 帮忙穷举了可能的攻击路径
- **代码生成**：编辑器工具（Text→TMP 转换、Tilemap 生成）的结构性代码
- **文档撰写**：项目设计文档、构建备忘录

核心经验：AI 对「推理排查链路」和「穷举方案」这两个场景帮助最大；对「需要实际运行验证」的环节（如构建参数调整）只能提供方向，最终还是要靠真机测试。

## 四、如果重来一次

1. **先跑通「最小可玩 → 微信构建 → 真机验证」的闭环**，而不是在 Editor 里把功能做完再移植
2. **字体方案在第一个场景就搞定**，不要等项目大了再全量替换 Text→TMP
3. **主动分享需求直接砍掉**，从立项就用被动分享，不浪费时间排查
4. **非 Dev Build 问题设一个排查时间上限**（比如 2 天），到期没解决就接受水印，不等完美方案
5. **IL2CPP 构建从第二周就开始做**，每次加新模块就验一次，避免最后一次性处理堆积的兼容问题
