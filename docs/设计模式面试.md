# 设计模式 · 面试备考

> 面试官问「用过哪些设计模式」——不是考你背 23 种，是看你把日常代码提炼成模式后讲出来。
> 模式名是索引，重点是「项目里 XXX 地方有 XXX 痛点，所以我用了 XXX 模式，解决了 XXX」。

---

## 快速应考：10 个实际用过的模式

① 单例 —— MonoSingleton<T>，所有 Manager 共用
② 观察者 —— EventBus，解耦战斗/UI/音效
③ 对象池 —— GameObjectPool，复用怪物/子弹/特效
④ 工厂方法 —— SkillDefinitionBase.CreateRuntimeSkill，新技能不碰旧代码
⑤ 策略 —— ISkill，8 种技能同一接口、不同实现
⑥ 模板方法 —— UIPanelBase.OnOpen/OnClose，框架定流程、业务填内容
⑦ 外观 —— TableManager，外部不用管 FlatBuffers 底层
⑧ 中介者 —— UIManager，弹窗互相不引用、全通过 Manager 通信
⑨ 注册表 —— CombatTargetRegistry，避免 FindObjectsWithTag 全场景扫描
⑩ 组件模式 —— Unity/Cocos 基因自带，GameObject-Component

---

## 逐个展开

### ① 单例模式（Singleton）

**项目代码**：`MonoSingleton<T>`

**解决什么痛点**：全局只需要一个实例的东西——UIManager、TableManager、AudioService。如果每个要用到的地方都 `FindObjectOfType`，性能吃不住，代码到处飞。

**怎么实现的**：

```
// MonoSingleton<T> 泛型基类
//   - static T Instance
//   - Awake 处理：重复实例自毁 + DontDestroyOnLoad
// 所有 Manager 继承它：UIManager, TableManager, AudioService
```

**面试说**：游戏里单例避不开。我不手写——用泛型封装了 MonoSingleton<T> 基类，处理了两件事：场景切换不销毁 + 已存在时自毁。所有 Manager 继承就行。

---

### ② 观察者模式（Observer）

**项目代码**：`EventBus`

**解决什么痛点**：怪物死了 → 音效要播、UI 要更新击杀数、能量要掉落、结算要统计。如果 `EnemyBase` 里直接调四个模块的方法，强耦合。后面加成就系统又要改 `EnemyBase`。

```
EventBus.Subscribe<EnemyDiedEvent>(OnEnemyDied, owner: this);  // 音效订阅
EventBus.Subscribe<EnemyDiedEvent>(OnEnemyDiedStat);            // 结算订阅
EventBus.Subscribe<EnemyDiedEvent>(OnEnemyDiedDrop);            // 掉落订阅

// 战斗层只管发，谁收谁自己订阅
EventBus.Publish(new EnemyDiedEvent { enemy = boss, position = pos });
```

**核心设计**：泛型强类型事件——`Subscribe<EnemyDiedEvent>` 定义了什么事件触发什么回调，回调参数类型是确定的（不是 `object` 再 `as` 强转），编译期检查。支持 owner 自动清理——owner 被 Destroy 后自动取消订阅。

**面试说**：战斗模块跟 UI/音效/结算之间全走事件总线。核心是泛型强类型事件——不用 object 传参，每个事件类型独立路由。owner 被销毁时自动清理订阅，避免幽灵订阅 Bug。

---

### ③ 对象池（Object Pool）

**项目代码**：`GameObjectPool`

**解决什么痛点**：每帧产生/销毁几十个子弹和特效 → Instantiate + Destroy 频繁 → GC 分配 + 回收尖峰 → 间歇性卡顿。

```
// 预热
GameObjectPool.Prewarm(enemyPrefab, count: 50);
// 借
Bullet bullet = GameObjectPool.Get(bulletPrefab, pos, rot);
// 还
GameObjectPool.Release(bullet.gameObject);
```

**关键设计**：借出登记 LeasedObjects (HashSet) → 清池时精确销毁不做全场景扫描；maxInactive 上限防池无限膨胀；IPoolReceiver 回调让业务方在取用时重置状态；场景卸载自动 ClearAllPools。

**面试说**：写了一个轻量对象池。核心三点：借出登记解决清池时不做 FindObjectsOfType、maxInactive 上限防内存膨胀、IPoolReceiver 让业务方在取用时重置对象状态。子弹/怪物/特效全走池，GC 分配从每帧几十 KB 降到接近零。

---

### ④ 工厂方法（Factory Method）

**项目代码**：`SkillDefinitionBase.CreateRuntimeSkill`

**解决什么痛点**：技能类型持续增加——手枪、飞剑、符咒、手雷、闪电链……如果用 `switch(skillId)` 来 New，每加一个技能就要改 PlayerSkills——违背开闭原则。

```
SkillDefinitionBase (抽象基类)
  ├─ CreateRuntimeSkillInternal() → 子类各自实现（工厂方法）
  ├─ ApplyStatsToSkill() → 子类各自写入 per-level 数值
  └─ CreateRuntimeSkill() → 外部统一入口（框架层）

新增技能流程：
  创建 SO 子类 → 实现两个方法 → 拖进 SkillCatalog → 完成
  PlayerSkills 不用改一行代码
```

**面试说**：用工厂方法模式管技能创建。每个技能是一个 ScriptableObject 子类，自己负责创建自己的运行时实例。加新技能只需新建一个 SO 资产 + 实现两个方法，PlayerSkills 不用改。典型的开闭原则落地。

---

### ⑤ 策略模式（Strategy）

**项目代码**：`ISkill` 接口 + 8 种实现

**解决什么痛点**：8 种主动技能各有完全不同的行为——手枪是发射弹丸、手雷是抛物线范围爆炸、闪电链是跨帧雷击、轨道飞刃是环绕运动。但它们都需要同样的外部接口：每帧 Tick、升级、索敌。

```
ISkill 接口：
  - OnTick(dt) → 每种技能不同实现
  - Upgrade(level) → 升级

策略 A — SkillAutoProjectile（朝敌人发射直线弹丸）
策略 B — SkillThrowGrenade（抛物线 + 范围 AOE）
策略 C — SkillLightningStrike（随机选敌 + 逐道落雷）
策略 D — SkillOrbitingBlades（环绕玩家圆周运动）

上层 PlayerSkills 只调 skill.OnTick(dt)，不关心具体是哪一种
加新技能只加新策略类，不改上层调度代码
```

**面试说**：8 种主动技能全走策略模式——共用 ISkill 接口，上层只调 OnTick(dt)，不关心具体是手枪还是手雷。加新技能只加新策略类，不改上层。

---

### ⑥ 模板方法（Template Method）

**项目代码**：`UIPanelBase.OnOpen / OnClose`

**解决什么痛点**：弹窗打开 → 框架要做的事（入栈、排序、遮罩、中文字体、TimeScale 暂停）和业务要做的事（绑定数据、注册按钮）是两类操作，混在一起乱。

```
UIPanelBase（基类）：
  OpenByFramework() {
    框架定流程：入栈 → 排序 → 遮罩 → 暂停 → 字体 → OnOpen(payload)
  }
  OnOpen(payload) → virtual，子类重写
  OnClose() → virtual，子类重写

ShopPanel（子类）：
  OnOpen：绑定数据、刷新列表
  OnClose：清理注册的事件
```

**面试说**：UI 框架用了模板方法——UIPanelBase 定好弹窗生命周期骨架，子类只重写 OnOpen 绑定数据和 OnClose 清理资源。框架负责的排序、暂停、字体，业务层完全不用管。

---

### ⑦ 外观模式（Facade）

**项目代码**：`TableManager`

**解决什么痛点**：FlatBuffers 底层涉及二进制读取、IL2CPP 兼容处理、类型映射——外部调用方不关心这些。

```
外部视角（简单）：
  TableManager.Instance.GetTableItem<LevelWave>(101);

内部（复杂——外部不用管）：
  FlatBuffers .bytes 读取 → ByteBuffer 解析 → IFlatbufferObject 初始化
  → 字典缓存 → 类型映射 → IL2CPP 兼容
```

**面试说**：配表读取用外观模式——TableManager 对外只暴露 GetTableItem<T>(id)，内部 FlatBuffers 的二进制解析、IL2CPP 兼容、字典缓存在门面内部处理。外部一行代码，不碰底层。

---

### ⑧ 中介者模式（Mediator）

**项目代码**：`UIManager`

**解决什么痛点**：10 个弹窗，如果互相可以关对方——弹窗间互相引用，加一个新弹窗要改 3 个旧文件。中介者模式下，所有弹窗通信走 UIManager 或 EventBus，互相零引用。

```
不用中介者：
  ShopPanel 直接调 BagPanel.Instance.Refresh() → 强耦合

用了中介者：
  ShopPanel → EventBus.Publish(GoldChangedEvent) → BagPanel 自己订阅
  三者之间没有互相引用
```

**面试说**：UIManager 充当中介者——弹窗之间零直接引用，所有交互通过 UIManager（打开/关闭）或 EventBus（数据变更）中转。加一个新弹窗不需要改任何现有弹窗的代码。

---

### ⑨ 注册表模式（Registry Pattern）

**项目代码**：`CombatTargetRegistry`

**解决什么痛点**：`FindGameObjectsWithTag("monster")` 每帧遍历全场景 → 分配 `GameObject[]` → GC 频繁触发 → 间歇性卡顿。

```
EnemyBase.OnEnable → CombatTargetRegistry.Register(gameObject)
EnemyBase.OnDisable → CombatTargetRegistry.Unregister(gameObject)

技能索敌：
  CombatTargetRegistry.FindNearest("monster", player.pos, maxRange)
  → 只遍历活跃列表，零堆分配
```

**设计要点**：按 Tag 分桶存放活跃 Transform 列表；查询时顺手惰性剔除 null 引用；O(1) swap-with-last 删除。

**面试说**：不算 GoF 23 种里的，是自己提炼的。本质是「生命周期注册 + 惰性清理」——怪在 OnEnable 注册到按 Tag 分桶的字典，查询时顺便踢掉 null 引用。替代了 FindGameObjectsWithTag 的全局扫描和 GC 分配。

---

### ⑩ 组件模式（Component Pattern）

**不是写出来的模式，是 Unity / Cocos 引擎自带的**

GameObject-Component 本身就是设计模式的经典落地——不是继承一大堆类，而是把不同功能拆分到不同 Component 上。同一个 GameObject 想飞就挂 FlyComponent，想攻击就挂 AttackComponent。

**面试说**：Unity 和 Cocos 的 GameObject-Component 本身就是组件模式——用组合代替深层继承。我做技能系统也参考了这个思想——Skill 不是 Player 的子类，是挂在 Player 上的独立 Component，增删技能不改 Player 类。

## 两个引擎的写法对照

设计模式的思想跟引擎无关，但面不同岗位时开口说的代码例子要对。下面是同一批模式在两种引擎里的落地写法：

| # | 模式 | Unity / C# | Cocos Creator / TS |
|---|---|---|---|
| ① | 单例 | `MonoSingleton<T>` 泛型基类 | `static getInstance()` + `private constructor`；或挂 `cc.Node` 上走 `director.getScene()` 取 |
| ② | 观察者 | `EventBus.Subscribe<EnemyDiedEvent>(cb)` | `EventBus.on('enemy_died', cb)` 或包装 `new cc.EventTarget()` 做纯逻辑事件 |
| ③ | 对象池 | `GameObjectPool.Get(prefab)` + `Release(go)` | `cc.NodePool` —— Cocos 内置，`put(node)` / `get()`，对象放回时自动清理组件属性 |
| ④ | 工厂方法 | `SkillDefinitionBase.CreateRuntimeSkill()` —— ScriptableObject 子类实现 | `SkillFactory.create(type: SkillType): ISkill` —— 传枚举，内部 `switch` 或注册表映射到具体类 |
| ⑤ | 策略 | `ISkill` 接口 + 8 个 C# 类实现 | 一样的接口思路，TS 没有 `interface` 运行时检查，用抽象类 `abstract class SkillBase` 更稳 |
| ⑥ | 模板方法 | `UIPanelBase.OnOpen()` virtual + 子类 override | 一样的 `protected onOpen()` 抽象方法，TS 没有 `virtual/override` 关键字，方法直接重写 |
| ⑦ | 外观 | `TableManager.GetTableItem<T>(id)` 封装 FlatBuffers | `ConfigManager.get(key)` 封装 JSON/CSV，内部处理异步加载 + 缓存 |
| ⑧ | 中介者 | `UIManager.Open<ShopPanel>()` + `CloseTop()` | `UIManager.show("ShopPanel")` —— Cocos 通常用字符串/枚举路由面板 |
| ⑨ | 注册表 | `CombatTargetRegistry.Register(go)` 按 Tag 分桶 | Node 的 `group` 属性：`node.group = 'enemy'` + `cc.find('enemy')` 或用 `cc.director.getScene()` 遍历筛选 |
| ⑩ | 组件 | `AddComponent<Rigidbody>()` | `node.addComponent(cc.RigidBody)` —— 完全一样的哲学，只是 API 名字不同 |

**面 Cocos 岗时**，前 10 节讲设计思路和痛点（引擎无关），这节自然接上「同样一套模式在 Cocos 里这样落地」——面试官就明白你不是只会 C# 的 Unity 程序员。

**个别模式的详细 TS 写法**：

**单例**：
```typescript
class AudioManager {
    private static _instance: AudioManager;
    static getInstance(): AudioManager {
        if (!this._instance) this._instance = new AudioManager();
        return this._instance;
    }
    private constructor() {}  // 阻止外部 new
}
```

**对象池（Cocos 内置 NodePool）**：
```typescript
// Cocos 内置，不需要自己写
let pool = new cc.NodePool();
pool.put(node);            // 还
let node = pool.get();     // 借，池空时返回 null
// Cocos 的 NodePool 自动保留了节点的组件结构
```

**观察者（纯逻辑 EventTarget）**：
```typescript
// 不挂节点的纯逻辑事件
class GameEvents {
    private static _target = new cc.EventTarget();
    static on(event: string, cb: Function, target?: any) {
        this._target.on(event, cb, target);
    }
    static emit(event: string, ...args: any[]) {
        this._target.emit(event, ...args);
    }
}
```

**工厂方法（注册表模式，不用 switch）**：
```typescript
class SkillFactory {
    private static _registry: Map<SkillType, () => ISkill> = new Map();

    static register(type: SkillType, creator: () => ISkill) {
        this._registry.set(type, creator);
    }

    static create(type: SkillType): ISkill {
        return this._registry.get(type)?.();
    }
}
// 各技能类在模块加载时自注册，加新技能不改工厂代码
```

## 面试时怎么串起来说

> 设计模式在项目里用得很自然——不是为了用而用，是碰到具体问题自然引出来的。

> 单例和观察者是底层基础设施——所有 Manager 走单例，模块间通信走事件总线。工厂方法加策略模式管技能体系——SkillDefinitionBase 的 CreateRuntimeSkill 是工厂，ISkill 接口的 8 种实现是策略，加新技能不改旧代码。模板方法在 UI 框架里——UIPanelBase 定流程骨架，业务子类只填 OnOpen/OnClose。对象池和注册表是性能层——GameObjectPool 复用了所有频繁创建/销毁的对象，CombatTargetRegistry 替代了 FindObjectsWithTag 避免 GC 尖峰。外观模式用在 TableManager 上封装了 FlatBuffers 的复杂性。中介者让 UIManager 统一管理弹窗互调。

## 附：为什么 MVC 在游戏里不是核心

面试只答 MVC 会让人觉得你的认知停在大学水平——因为 MVC 在游戏引擎里本来就内置了：

```
M（数据）— ScriptableObject / FlatBuffers 表 / PlayerPrefs
V（视图）— Sprite + Animation + UI + 材质
C（控制）— MonoBehaviour 组件逻辑

Unity / Cocos 的 GameObject-Component 天生就是 MVC 的变体
```

所以你用 MVC 是对的——只是不说也不会丢分，因为这就是引擎的正常工作方式。要讲的不是 MVC，是「在 MVC 之上你又加了什么模式来解决具体问题」。
