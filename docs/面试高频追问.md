## 一、资源合图批处理 & 纹理压缩

### 1.1 什么是合图（Sprite Atlas / 图集）

**问题**：一个 UI 界面有 50 个小图标，每个图标一张 PNG。每个 PNG 对 GPU 来说是一次独立的 Draw Call（绘制调用）→ 50 次 Draw Call → 渲染管线频繁切换纹理 → 性能差。

**合图的思路**：把 50 张小图拼成 1 张大图，GPU 一次 Draw Call 渲染整张图，用 UV 坐标裁剪显示需要的部分。

```
合图前：50 个文件，50 次 Draw Call
  [icon1.png] [icon2.png] [icon3.png] ... [icon50.png]

合图后：1 个文件，1 次 Draw Call
  ┌──────────────────────────────┐
  │ icon1 │ icon2 │ icon3 │ ...  │
  │──────────────────────────────│
  │ icon16│ icon17│ icon18│ ...  │
  │──────────────────────────────│
  │ ...                         │
  └──────────────────────────────┘
```

**Unity 里的做法**：把图标放入同一个 Sprite Atlas Asset → 打包时 Unity 自动合并 → 运行时用 `sprite.name` 引用，Unity 自动处理 UV 映射。

**为什么叫"批处理"**：不是手动一个一个拖，而是写编辑器工具脚本批量扫描所有图标 → 按尺寸/用途自动分组 → 批量生成 Sprite Atlas → 批量替换引用。一个项目几百上千张图，不批量处理根本做不完。

### 1.2 纹理压缩（个人项目里的实践）

**问题**：一张 1024×1024 的 PNG，RGBA 32-bit，在内存里占 1024 × 1024 × 4 = **4MB**。同屏几十张这样的图，内存直接炸。

**纹理压缩的原理**：不是 PNG/JPEG 那种文件压缩（文件小但加载到内存还是大），而是**改变 GPU 的纹理存储格式**，让纹理在显存/内存里的占用直接变小。

| 格式 | 每像素 | 1024×1024 占用 | 透明度 | 适用平台 |
|---|---|---|---|---|
| RGBA32（原始） | 32 bit | 4 MB | ✅ | 编辑器 |
| **ASTC** 6×6 | ~3.5 bit | ~0.43 MB | ✅ | iOS / Android 主流 |
| ETC2 | 4-8 bit | 0.5-1 MB | ✅ | Android |
| DXT5 | 8 bit | 1 MB | ✅ | PC |
| RGB Crunched | 可变 | 可变 | ❌ | 不需要透明的纹理 |

**效果**：4MB → 0.43MB，直接省了 90%。

**个人项目的实践**：

在微信小游戏里，纹理压缩直接影响分包体积和运行时内存：

```
微信小游戏使用 WebGL 2.0 → 支持 ETC2 / ASTC
Unity Texture Importer 设置：
  - Texture Type: Sprite (2D and UI)
  - Compression: ASTC 6×6（移动端）/ DXT5（PC 开发调试）
  - 不需要透明的图关闭 Alpha 通道 → 再省 25%
```

在 [docs/cdn-analysis.md](docs/cdn-analysis.md) 里有详细的纹理优化记录：bg_01.jpg 从 764KB 压到 188KB、地图纹理集用 ASTC 压缩约 0.5MB、计划中的去除不需要的 Alpha 通道。

**面试怎么讲**：

> Unity 的 Sprite Atlas 把多张小图合成一张大图，减少 Draw Call。纹理压缩是改变 GPU 的纹理存储格式——ASTC 6×6 可以把 4MB 的纹理压到 0.4MB，在显存里直接生效，不是文件级别的压缩。两个手段配合：合图减少渲染切换次数，压缩减少显存占用。

### 1.3 追问：Draw Call 是什么

> CPU 告诉 GPU "画这个东西" 的指令。每次切换材质/纹理/Shader → 就要发一个新 Draw Call。合图的核心目的就是让多个 UI 元素共享同一张纹理 → 减少纹理切换 → 降低 Draw Call。手机游戏通常控制在 100 次以内，超过就开始卡。

## 二、模块化拆分与多语言适配

### 2.1 模块化拆分

**场景**：《御剑三国》同时跑韩服、日服、台服、东南亚服等 10+ 语言区域。如果所有语言的文件混在一起 → 包体巨大、改一个语言可能影响其他语言、运营需求不同步。

**拆分思路**：

```
核心工程（共用逻辑）
├── 战斗系统
├── UI 框架
├── 网络模块
└── 数据表结构（表头统一）

语言/渠道模块（独立打包）
├── 中文简体（zh-CN）
│   ├── 本地化文本表
│   └── 特定 UI 资源（简体字字体/书法风格图片）
├── 日语（ja-JP）
│   ├── 本地化文本表
│   └── 特定 UI 资源（日文字体/和风图片）
└── 韩语（ko-KR）
    ...
```

### 2.2 多语言适配：配置表方案（你说的那种）

```
多语言文本表（Excel / CSV）
┌──────────┬──────────────┬──────────────┬──────────────┐
│ TextID   │ zh-CN        │ en-US        │ ja-JP        │
├──────────┼──────────────┼──────────────┼──────────────┤
│ LOGIN_BTN│ 登录         │ Login        │ ログイン     │
│ SHOP_TTL │ 商城         │ Shop         │ ショップ     │
│ SKILL_01 │ 雷霆一击     │ Thunder      │ 雷撃         │
└──────────┴──────────────┴──────────────┴──────────────┘

运行时：
  string lang = PlayerPrefs.GetString("lang", "zh-CN");
  string text = TableManager.Get("Localization", "LOGIN_BTN")[lang];
  → "登录"
```

**优点**：策划可以直接改 Excel，不需要程序员介入。一条记录能覆盖所有语言，不易漏。

**缺点**：长文本（剧情对话）放 Excel 里很难维护——列太宽、换行乱、不好预览。

### 2.3 Git 分支方案（也是你说的那种）

```
main ← release 分支，不含渠道差异
├── feat/cn-android    ← 国内安卓
├── feat/cn-ios        ← 国内 iOS
├── feat/kr            ← 韩国
├── feat/jp            ← 日本
```

**工作方式**：共用代码在 main，渠道特定改动在各分支。发版时切到对应分支构建。

**优点**：隔离性强，改一个渠道不会影响其他。

**缺点**：分支多了合并地狱——main 改了一个 Bug，10 个分支都要合一遍。

### 2.4 更好的方案：Google Sheet + 自动化管线

这是目前工业级项目（头部 SLG / 二次元手游）用得比较多的做法，结合了你现在的方案但更自动化：

```
Google Sheet（多人协作编辑）
  ↓ 脚本自动导出
JSON / CSV 文件（每个语言一个文件）
  ↓ CI/CD 构建时
打进对应渠道包（不再需要 Git 分支管理渠道）
```

**关键差异**：

| | Excel + Git 分支 | Google Sheet + 管线 |
|---|---|---|
| 翻译协作 | 离线 Excel，邮件传来传去 | 多人实时在线编辑 |
| 渠道管理 | 每个渠道一个 Git 分支 | 构建脚本按参数切语言 |
| 翻译审核 | 手动比对 | API 接入翻译平台（如 Crowdin/Lokalise） |
| 漏翻检测 | 人工检查 | CI 自动比对 key 数量 + 占位符 |
| 长文本 | Excel 列挤成面条 | Google Sheet 单元格也挤，但可以接翻译平台 |

**进阶方案（大厂做法）**：

```
1. 文本 key 管理：Excel → 导出 JSON
2. 翻译：接入 Crowdin / Lokalise API
   - 策划新增 key → 自动推送到翻译平台
   - 翻译人员在线翻译 → 审核通过 → API 回调拉回 JSON
3. 构建：CI 按 target_lang 参数 → 打包对应语言文件 → 生成渠道包
4. 分支策略：只有 main 一个分支，渠道差异靠配置文件 + 构建参数
```

### 2.5 图片/UI 层面的多语言

文字之外还要处理：

- **字体**：中文用中文字体，日文用日文字体，阿拉伯文要 RTL（从右到左）布局
- **图片含文字**：按钮图上的「开始游戏」四个字 → 每个语言要单独出图，或改用 Text 组件实时渲染
- **UI 布局**：德语一个词是中文的 3 倍长 → 按钮要自适应宽度 → 或用缩略版翻译
- **占位符**：`"您获得了 {0} 金币"` → `"You got {0} gold"` → 不同语言 {0} 位置可能不同 → 不能用 `string.Replace`，要用 `string.Format`

### 2.6 面试怎么讲

> 核心是配置表驱动 + 渠道隔离。文本放在多语言配置表里，按 TextID 查询，当前语言由 PlayerPrefs 控制。渠道特定资源（字体、含文字图片）按文件夹分开放。之前用 Git 分支管理渠道差异，后来改成了构建参数 + CI 管线——渠道配置和代码分离，一个分支就能出所有渠道包换。如果需要翻译平台对接，可以接入 Crowdin 或者 Google Sheet 自动导出。

## 三、ProtoBuf vs JSON

### 3.1 先搞清楚：它们都是序列化协议

```
客户端                                服务器
  │                                     │
  │  发送数据：{ "hp": 100, "pos": ...}  │
  ├────────────────────────────────────→│
  │                                     │
  │             收到响应                 │
  │←────────────────────────────────────┤
  │                                     │
```

**协议做的事情**：把内存里的数据结构（类/对象） → 变成一堆字节 → 发给对方 → 对方还原成数据结构。

### 3.2 JSON 怎么做

```json
{
  "playerId": 10001,
  "name": "玩家张三",
  "hp": 100,
  "position": { "x": 12.5, "y": 3.7 },
  "items": [
    { "id": 1, "count": 5 },
    { "id": 2, "count": 3 }
  ]
}
```

**流程**：对象 → `JsonUtility.ToJson()` → 字符串 → `Encoding.UTF8.GetBytes()` → 发出去。收到后反向操作。

**优点**：
- 人类可读，直接看能懂
- 抓包调试方便
- 几乎所有语言都有内置支持

**缺点**：
- **体积大**：字段名重复存储（`"playerId"` 出现两次，`"name"` 占了 6 个字节，实际数据才 12 个字节）
- **解析慢**：字符串解析 → 逐个字符判类型 → 字符串转数字 → 构建对象
- **没有 Schema**：字段拼错只能在运行时发现，编译期不报错

### 3.3 ProtoBuf 怎么做

先定义 `.proto` 文件（Schema）：

```protobuf
message PlayerData {
  int32 player_id = 1;     // 字段用数字编号，不是字符串名
  string name = 2;
  int32 hp = 3;
  Position position = 4;
  repeated Item items = 5;
}

message Position {
  float x = 1;
  float y = 2;
}
```

**流程**：`.proto` 文件 → `protoc` 编译器 → 生成 C# 强类型类 → `PlayerData.ToByteArray()` → 直接发二进制 → 对方 `PlayerData.Parser.ParseFrom(bytes)` → 还原。

**传输的是二进制，不是 JSON 文本**：

```
JSON（文本）：{"playerId":10001,"name":"玩家张三","hp":100}
  → 约 55 字节（取决于编码）

ProtoBuf（二进制）：08 11 27 12 0C E7 8E A9 E5 AE B6 E5 BC A0 E4 B8 89 18 64
  → 约 18 字节（同一条数据）
```

### 3.4 对比

| | JSON | ProtoBuf |
|---|---|---|
| 格式 | 文本字符串 | 二进制 |
| 体积 | 大（字段名重复存储） | 小（数字编号 + Varint 编码） |
| 解析速度 | 慢（字符串解析） | 快（二进制直接映射） |
| 可读性 | 人类可读，抓包直接看 | 二进制，需要工具反序列化 |
| Schema | 无（运行时校验） | 有（`.proto` 编译期校验，字段类型不对编译不过） |
| 版本兼容 | 手写兼容逻辑 | 内置向前/向后兼容（新增字段给默认值） |
| 调试 | 方便（看得懂） | 不方便（需要 proto 文件 + 工具） |
| 适用场景 | Web API、配置文件 | 游戏网络通信、数据存储 |

### 3.5 为什么游戏用 ProtoBuf 而不是 JSON

**第一，包体小 = 流量省 + 延迟低**。MOBA/SLG 每帧同步的数据量，用 JSON 可能 5KB，ProtoBuf 可能 1KB。移动网络不稳定时，1KB 比 5KB 丢包率和重传概率都低得多。

**第二，Schema 是双刃剑——在游戏里是好处**。`.proto` 文件就是前后端的数据合同。服务端改了 `PlayerData` 的字段类型 → C# 编译直接报错 → 不会上线后才炸。JSON 没有这个保护——字段拼错只能在运行时发现。

**第三，版本兼容**。ProtoBuf 的字段编号机制天然支持新增/废弃字段：

```protobuf
message PlayerData {
  int32 player_id = 1;
  string name = 2;        // v2.0 废弃
  int32 hp = 3;
  string display_name = 4; // v2.0 新增——旧客户端收到后忽略，默认空字符串
}
```

旧客户端用旧 proto 解析新数据 → 不认识字段 4 → 跳过，不报错。JSON 做不到——所有字段都会解析，客户端不认识的字段要么忽略要么报错，而且没有 Schema 你不知道哪个字段是新加的。

### 3.6 ProtoBuf 的缺点

- **不可读**：抓包看到一堆十六进制，调试必须配合 proto 文件 decode
- **需要编译步骤**：`.proto` → 生成代码，增加构建流程
- **不适合超小数据**：几个字节的数据 ProtoBuf 的序列化开销可能比数据本身还大
- **动态类型不友好**：必须提前定义消息结构，不能在运行时随意拼 JSON

### 3.7 面试怎么讲

> 游戏网络通信对包体大小和解析速度敏感。ProtoBuf 是二进制序列化，字段用数字编号代替字符串名，用 Varint 变长编码压缩整数——同一条数据比 JSON 小 60-70%。更重要的是有 Schema 约束：`.proto` 文件是前后端的数据合同，字段类型不对编译就报错，不会留到线上炸。向前向后兼容——服务端加字段，旧客户端忽略不认识的，不报错。缺点是不可读、调试需要工具。

## 五、CPU 瓶颈 vs GPU 瓶颈：怎么判断卡顿是谁的锅

### 5.1 第一反应：降低分辨率

这是最快的判断手段，不需要任何工具：

> 把游戏分辨率从 1920×1080 降到 1280×720（或 960×540）

| 降分辨率后 | 结论 |
|---|---|
| **帧率明显回升** | **GPU 瓶颈**。像素少了，GPU 画得动了 |
| **帧率几乎不变** | **CPU 瓶颈**。像素再少，CPU 算不动还是算不动 |

**原理**：降分辨率只减轻 GPU 的像素填充（Fill Rate）和片段着色负担，对 CPU 的逻辑计算量没有影响。所以这个测试直接区分了「画不动」还是「算不动」。

### 5.2 第二反应：Unity Profiler 看 Timeline

有工具的情况下，直接开 Unity Profiler，看 CPU Usage 和 GPU Usage 两条线：

```
Profiler 时间线视图：

帧时间 33ms（30FPS 预算）
├── CPU: ████████████████████████████████ 32ms  ← 几乎全满
└── GPU: ██████ 6ms                          ← 很闲

→ 结论：CPU 瓶颈。GPU 在等 CPU 给指令。
```

```
帧时间 33ms
├── CPU: ██████ 6ms                          ← 很闲
└── GPU: ████████████████████████████████ 32ms  ← 满的

→ 结论：GPU 瓶颈。CPU 干完了在等 GPU 渲染。
```

**CPU 栏再展开细看**：

| 哪项占比高 | 问题方向 |
|---|---|
| `Scripts` 占比高 | 业务逻辑（Update、协程、GC）→ 查自己的代码 |
| `Physics` 占比高 | 碰撞体太多 → 减少 Collider 或用 Tilemap Collider |
| `Camera.Render` 占比高 | CPU 端的渲染准备（提交 Draw Call）→ 合图、减少材质种类 |
| `GC.Collect` 占比高 | 堆内存分配频繁 → 查临时对象、装箱、字符串拼接 |

**关于装箱的补充说明**：

C# 的数据类型分为值类型（`int`, `float`, `bool`, `struct`）和引用类型（`class`, `string`, `object`）。值类型在栈上，GC 不管。引用类型在堆上，用完要 GC 回收。

**装箱就是：把值类型强行塞进 `object` 壳子里，在堆上分配了一块本不需要的内存。**

```csharp
int hp = 100;                // 值类型，栈上，零堆分配
object boxed = hp;           // 装箱！堆上 new 了一个 object
int unboxed = (int)boxed;    // 拆箱：object → int（不分配，但有一次类型校验 + 拷贝）
```

**只有装箱，没有"其他箱"**。但拆箱和以下几种操作跟装箱一样是 GC 压力的常见来源：

| 操作 | 会分配堆内存？ | 示例 |
|---|---|---|
| **装箱 (Boxing)** | ✅ 分配 | `object o = 5;` |
| **拆箱 (Unboxing)** | ❌ 不分配（但有类型校验开销） | `int i = (int)o;` |
| **数组分配** | ✅ 分配 | `new int[100]`, `FindObjectsWithTag` 返回的 `GameObject[]` |
| **字符串拼接** | ✅ 分配（string 不可变，每次拼接都 new） | `"a" + "b" + "c"` → 循环里拼字符串是重灾区 |
| **闭包捕获** | ✅ 分配（编译器生成匿名类） | Lambda 里用了外部局部变量 → `() => localVar` |
| **LINQ** | ✅ 分配（迭代器对象） | `.Where()`, `.Select()` 在 IL2CPP 下分配更严重 |
| **协程 yield return 值类型** | ✅ 装箱 | `yield return 0;` → int 装箱成 object |
| **Dictionary 用 enum 做 key** | ✅ 装箱（取 hash code 时） | `dict[MyEnum.A]` → enum 装箱 |

Unity Profiler 里 `GC.Alloc` 列会标出每帧分配了什么类型——看到 `System.Int32`、`System.Single` 冒出来，就是装箱。看到 `GameObject[]`、`System.String`，就是数组和字符串分配。定位到来源就能对症下药。

### 5.3 没有 Profiler 怎么办（微信小游戏真机调试）

微信开发者工具的性能面板只能看整体 FPS 和内存，没法拆 CPU/GPU。这时候靠经验推断：

**CPU 瓶颈的典型症状**：
- 敌人多时卡，敌人少时流畅（逻辑量跟敌人数量正相关）
- 暂停界面时依然卡（UI 还在 Update 轮询、协程没停）
- 卡顿是**间歇性尖峰**（GC 触发 → 猛卡一下 → 恢复）
- `Time.timeScale = 0` 后帧率恢复正常

**GPU 瓶颈的典型症状**：
- 满屏粒子特效时卡，特效消了就流畅
- 地图上植被/装饰物多时卡
- 切换镜头看空旷区域时帧率回升
- 降分辨率立即见效（回到 5.1 的测试）

### 5.4 实际处理过的案例

**案例 1：波次开始时猛卡 → CPU 瓶颈（文字割草机）**

现象：新一波怪物刷新瞬间，帧率从 30 掉到 8-10，持续约 0.5 秒后恢复。

排查：`SpawnerWaves` 在同一帧 Instantiate 50+ 个怪物 → Unity 的 `Instantiate` 内部有序列化数据反序列化 + `Awake` + `OnEnable` 调用 → 单帧 CPU 尖峰。

解决：引入 `SpawnLimiter`，限制每帧最多生成 5 个 → 50 个分摊到 10 帧 → CPU 负载平滑。这就是文档中「分帧生成」的优化。

**案例 2：同屏 200 敌时持续低帧率 → 先降分辨率确认是 GPU**

现象：同屏敌人超 200 后帧率掉到 15，不管敌人动不动都卡。

测试：把分辨率降到 1280×720 → 帧率回到 28。确认 GPU 瓶颈。

解决：敌人 Sprite 每帧都在重绘 → 启用 Sprite Atlas 合图 → Draw Call 从 200+ 降到几十 → GPU 的渲染提交不再排队。

**案例 3：GC 间歇性卡顿 → CPU 瓶颈的特殊类型（文字割草机）**

现象：运行时不定期猛卡 100-200ms，之后恢复正常。监控 `Time.deltaTime` 偶尔跳到 0.2 秒。

排查：排除法——降分辨率无效（不是 GPU）、卡顿时机不固定（不是刷怪）、Profiler 看 GC.Alloc 每帧几百 KB → 堆分配频繁触发 GC。

定位到 `FindGameObjectsWithTag` 每次调用分配新数组 → 改为 `CombatTargetRegistry` → GC 分配降到接近零 → 间歇性卡顿消失。

### 5.5 排查思路总结

```
卡顿 → 降分辨率
         ↓
    帧率回升？──是──→ GPU 瓶颈
         │             └→ 合图、减少 Draw Call、纹理压缩、降低粒子数
         │
         否
         ↓
    CPU 瓶颈
      ├→ Profiler 看 Scripts/Physics/GC 占比
      ├→ 间歇性尖峰 → 查 GC 分配（堆上临时对象）
      ├→ 持续偏高 → 查 Update/协程轮询、碰撞检测、寻路
      └→ 项目侧的实践 → 分帧生成、对象池、索敌注册表
```

### 5.6 面试怎么讲

> 第一反应是降分辨率——分辨率降了帧率回升就是 GPU 瓶颈，不变就是 CPU 瓶颈，这是最快的二分法定性。有 Profiler 的话直接看 CPU Usage 和 GPU Usage 两条线谁的 bar 更长。之前做割草类游戏时处理过两类典型案例：波次同时刷几十只怪导致单帧 CPU 尖峰——用分帧生成解决；同屏 200 敌人 GPU 渲染跟不上——用 Sprite Atlas 合图减少 Draw Call。还有一个是 GC 间歇性卡顿，用 CombatTargetRegistry 替代 FindObjectsWithTag 消除了堆分配。

## 五-B、多端同步与弱机适配

> 面试官可能问"组队时不同机型性能不一样怎么办"——这个问题同时考你渲染管线理解和多人同步认知。

### 5B.1 核心矛盾

两台手机，A 机稳 30 FPS，B 机偶尔掉到 15 FPS。如果游戏逻辑跟帧率挂钩，两边世界状态会发散——快机上怪走了三步，慢机上才走一步。

### 5B.2 第一道防线：逻辑跟渲染解耦

**绝不能用 `deltaTime` 直接驱动逻辑**——浮点误差会累积，两边算出不一样的结果。

```csharp
// ❌ 每帧累加 deltaTime → 浮点误差积累 → A 机和 B 机时间轴会慢慢漂移
position += direction * speed * Time.deltaTime;

// ✅ 用固定时间步长（FixedUpdate），战斗/物理逻辑全在这跑
// Time.fixedDeltaTime = 1/30s → 不管帧率多少，逻辑每秒执行固定 30 次
```

但这只解决单机问题。多人场景下还有第二个矛盾。

### 5B.3 第二道防线：三种同步模型

| 模型 | 怎么工作 | 快机等慢机？ | 适用游戏 |
|---|---|---|---|
| **帧同步（Lockstep）** | 所有人等最慢的人，一帧一帧对齐 | ✅ 等，快机空转 | 王者荣耀、LOL、RTS |
| **状态同步（State Sync）** | 服务端算 → 下发结果 → 客户端只负责渲染 | ❌ 不等，但看的是"过去" | MMORPG、大多数手游 |
| **乐观帧同步** | 不等，慢机看到的画面是插值后的旧数据 | ❌ 不等，但慢机观感差 | 吃鸡类、FPS |

**帧同步**：服务端等所有客户端上报"我这帧好了"→ 一起推进下一帧 → 一个人卡，全房间陪卡。王者 460 就是这个——不一定是你自己卡。

**状态同步**：服务端独立跑逻辑 → 定时广播世界状态 → 客户端收到后渲染。缺点是客户端看到的状态永远是服务端 N 毫秒前的快照。

### 5B.4 分帧加载在多人下的处理

分帧加载只影响**表现层**（什么时候画出来），不影响**逻辑层**（怪什么时候开始生效）：

```
服务端逻辑层：
  波次 3 开始 → 50 只怪一瞬间全部 Active（没有分帧概念）

客户端表现层：
  A 机（快）：分 10 帧逐个显示 → 第 10 帧所有怪可见
  B 机（慢）：分 20 帧逐个显示 → 第 20 帧所有怪可见

  碰撞/伤害/血量 → 服务端统一算，客户端只管"看"
```

**核心原则**：分帧加载是视觉平滑，不是逻辑同步。怪物的激活时间、位置、血量由服务端统一决策。

### 5B.5 B 机实在太慢怎么办

| 做法 | 触发条件 | 效果 |
|---|---|---|
| **动态降画质** | 帧率 < 20 持续 1 秒 | 自动降分辨率、关粒子、关阴影 → 帧率回升 |
| **减少渲染单位** | 同屏超过设备预算 | 最远的怪不渲染（逻辑照跑，伤害照算） |
| **减少分帧摊分数** | 帧率 < 20 | 正常 10 帧分完，弱机 5 帧分完（跳一下但不卡太久） |
| **踢人 / 托管** | 帧率 < 5 持续 3 秒 | 服务端托管该玩家 → 自动跟随队友 |

### 5B.6 面试怎么讲

> 多人不同机型的问题分两层。第一层是逻辑和渲染解耦——FixedUpdate 固定步长跑逻辑，Update 按设备帧率跑渲染，分帧加载只影响渲染的视觉平滑，逻辑层不受设备帧率影响。第二层是多人同步模型——帧同步等最慢的人，状态同步不等但看的是服务端过去的状态，根据游戏类型选。实际项目里加动态降画质保底——帧率掉到阈值自动砍特效和分辨率。

## 六、UI 框架设计（UIManager + UIPanelBase）

> 简历写了"搭建 UGUI 弹窗框架"，面试官会问：为什么不用 Unity 原生方案、怎么设计的、栈和确认框什么关系。

### 6.1 架构：双层面板系统

```
┌──────────────────────────────────────┐
│           Overlay Layer               │  overlayRoot (sortingOrder ≥ 800)
│  ┌──────────────────────────────┐    │
│  │    UiConfirmDialog (确认框)    │    │  ← 独立层，不参与栈
│  ├──────────────────────────────┤    │
│  │    UiToastPanel (轻提示)      │    │
│  └──────────────────────────────┘    │
├──────────────────────────────────────┤
│            Stack Layer                │  stackRoot (sortingOrder 200+)
│  ┌──────────────────────────────┐    │
│  │  Panel C   (栈顶，可见)       │    │  ← 后进先出，同类型唯一实例
│  ├──────────────────────────────┤    │  ← 下层自动隐藏
│  │  Panel B   (隐藏)             │    │
│  ├──────────────────────────────┤    │
│  │  Panel A   (隐藏)             │    │
│  ├──────────────────────────────┤    │
│  │       共用遮罩 (可选)          │    │
│  └──────────────────────────────┘    │
└──────────────────────────────────────┘
```

**设计决策**

| 问题 | 方案 | 为什么 |
|---|---|---|
| 弹窗怎么叠 | 主栈（LIFO 后进先出） | 玩家体感是"一层一层打开，一层一层关闭"，跟手机 App 一致 |
| 确认框怎么处理 | 独立 Overlay 层 | 确认框不应该把下面的弹窗关掉——点了"取消"还要回到刚才的界面 |
| 同类型弹窗能开多个吗 | ❌ 唯一实例 | 开第二个 ShopPanel 会把第一个抬到栈顶并刷新，不会创建两份 |
| 打开已有的弹窗 | 关掉它上面的层 → 抬到栈顶 → 再次 OnOpen | 复用实例，不重新创建 |
| 暂停游戏？ | 引用计数暂停栈 | 第一层弹窗打开暂停，最后一层关闭恢复——不会因为关中间一层就误恢复 |

**几个术语先搞清楚**：

| 术语 | 全称 | 大白话解释 |
|---|---|---|
| **LIFO** | Last In, First Out | 后进先出——叠盘子，最后放上去的最先拿下来。弹窗也是：最后打开的最先被关 |
| **栈 Stack** | — | 就是按 LIFO 规则存取数据的容器。`Push` 压进去，`Pop` 弹出来 |
| **模态 Modal** | — | 弹窗开着时下面的东西不能点。跟"非模态"（弹窗放旁边，还能操作下面）相对 |
| **Overlay** | — | 覆盖层，浮在主栈之上的独立层。确认框放 Overlay 不走栈，关了下面界面还在 |

### 6.2 UIManager：核心控制器

**Inspector 配置**：

```csharp
[SerializeField] private RectTransform stackRoot;      // 主栈父节点
[SerializeField] private RectTransform overlayRoot;    // Overlay 父节点
[SerializeField] private Image stackBackdrop;          // 共用遮罩（可选）
[SerializeField] private List<GameObject> panelPrefabs; // 注册所有弹窗 Prefab
[SerializeField] private UiConfirmDialog confirmDialogPrefab; // 确认框
[SerializeField] private UiToastPanel toastPanelPrefab;      // Toast
[SerializeField] private int stackSortingBase = 200;   // 主栈起始 sortingOrder
[SerializeField] private int overlaySortingBase = 800; // Overlay sortingOrder
```

**内部数据结构**：

```csharp
// Prefab 注册表：Type → Prefab（Awake 时从 panelPrefabs 列表构建）
Dictionary<Type, GameObject> _prefabByType;

// 实例缓存：Type → 运行时实例（唯一实例约束）
Dictionary<Type, UIPanelBase> _instanceByType;

// 主栈：List 底→顶
List<UIPanelBase> _stack;

// 暂停引用计数
int _pauseLocks;
float _storedTimeScale;
```

### 6.3 Open<T> 的完整流程

```csharp
public T Open<T>(object payload, UiOpenOptions options) where T : UIPanelBase
{
    // ① 类型安全检查 —— 防止误用 Open<UiConfirmDialog>()
    if (type == typeof(UiConfirmDialog)) return null;  // 应使用 ShowConfirm()

    // ② 关掉确认框（新面板打开时不希望确认框挡在上面）
    CloseConfirmSilently();

    // ③ 取或创建实例（同类型唯一）
    var panel = GetOrCreateInstance(type);
    //    └→ _instanceByTable 有 → 复用
    //    └→ 没有 → Instantiate(prefab) 或 new GameObject + AddComponent

    // ④ 栈管理
    if (_stack.Contains(panel))
        // 已在栈中 → 关掉它上面的层 → 抬到栈顶
        while (_stack.Count - 1 > idx) PopTopInternal();
    else
        // 不在栈中 → 隐藏当前栈顶 → 入栈 → 显示
        _stack[^1].SetActive(false);
        _stack.Add(panel);
        panel.SetActive(true);

    // ⑤ 应用选项 → OnOpen → 中文字体 → 刷新遮罩 → 刷新排序
    ApplyOpenOptions(panel, options);
    panel.OnOpen(payload);
    BattleChineseFontRuntime.ApplyToHierarchy(panel.transform);
    RefreshStackBackdrop();
    RefreshStackSorting();
}
```

### 6.4 暂停栈：引用计数

```csharp
// 打开第一个弹窗（PauseTime=true）
_pauseLocks: 0 → 1
_storedTimeScale = 1.0
Time.timeScale = 0    // ← 游戏暂停

// 打开第二个弹窗（PauseTime=true）
_pauseLocks: 1 → 2
// Time.timeScale 已经是 0，不需要再改

// 关闭第二个弹窗
_pauseLocks: 2 → 1
// Time.timeScale 还是 0（还有其他弹窗锁着）

// 关闭第一个弹窗
_pauseLocks: 1 → 0
Time.timeScale = _storedTimeScale = 1.0  // ← 恢复
```

关键点：**不是"开一个暂停、关一个恢复"，而是引用计数——只有最后一个暂停锁释放才恢复**。这防止了"弹窗 A 上面开了弹窗 B，关了 A 游戏就恢复（实际上 B 还开着）"的 Bug。

### 6.5 Canvas 排序

```csharp
// 主栈：每层 +10
// 栈底 Panel A: sortingOrder = 200 + 10 = 210
// Panel B:      sortingOrder = 200 + 20 = 220
// 栈顶 Panel C: sortingOrder = 200 + 30 = 230

// Overlay 永远在主栈之上
// UiConfirmDialog: sortingOrder = 800

// 刷新时机：每次 Open / CloseTop / CloseAll 后
// 要求：弹窗 Prefab 根节点挂 Canvas，勾选 Override Sorting
```

### 6.6 确认框：弱 B 模式

确认框不走 `Open<T>()`，而是单独一套流程 `ShowConfirm()`：

```csharp
// 为什么确认框要独立？
// 场景：选卡界面上弹了确认"确定选择这张卡吗？"
//   - 如果确认框走主栈 → 选卡界面被 Pop 掉了 → 点取消回不去了
//   - 确认框走 Overlay → 选卡界面在栈里不变 → 取消后还在
```

**确认框跟主栈的交互规则**：

```
① Escape/返回键：
   先关确认框（如果开着）→ 再关主栈顶

② Open<T>() 时：
   自动关掉确认框（新面板不需要旧确认框挡着）

③ 暂停行为：
   确认框也参与引用计数暂停（PauseTime=true 时一样加锁）
```

### 6.7 使用时只需要三步

以项目中实际存在的 `ShopView` 为例：

```csharp
// 步骤 1：创建 Prefab
//   ShopPanel.prefab → 根节点挂 ShopView 组件（继承 UIPanelBase）

// 步骤 2：UIManager Inspector 注册
//   把 ShopPanel.prefab 拖进 UIManager.panelPrefabs 列表

// 步骤 3：业务调用
// 打开
var panel = UIManager.Instance.Open<ShopView>(shopData);
//                                 ↑ 泛型自动匹配 Prefab 类型

// ShopView 内部
public class ShopView : UIPanelBase
{
    public override void OnOpen(object payload)
    {
        var data = payload as ShopData;  // 强转
        // 绑定数据 → 刷新列表 → 注册按钮事件
    }

    public override void OnClose()
    {
        // 清理按钮事件、协程等
    }
}

// 关闭（业务层调用或框架层 Escape 触发）

```

### 6.8 跟 Unity 原生方案对比

| 需求 | Unity 原生 | 本项目方案 |
|---|---|---|
| 多个弹窗叠加 | 各自管理，排序靠手动调 sibling | 栈自动管理，sortingOrder 自动递增 |
| 弹窗间互斥 | 手写判断逻辑 | 同类型唯一实例，自动抬到栈顶 |
| 弹出时暂停游戏 | 手写 `Time.timeScale = 0` | 引用计数暂停栈，自动管理 |
| 确认对话框 | 手写或买插件 | `ShowConfirm()` 一行调 |
| 返回键处理 | 每个弹窗各自写 | UIManager.Update 统一处理 |
| TMP 中文字体 | 每个 Prefab 手动指字体 | `Open` 时自动对子树执行 `ApplyToHierarchy` |
| 关闭全部弹窗 | 遍历查找 → 逐个关 | `CloseAllStack()` |

### 6.9 面试怎么讲

> UI 框架的核心设计是双层面板系统——主栈走 LIFO 模态栈，确认框走独立 Overlay 层。弹窗按类型做了唯一实例约束，泛型 `Open<T>()` 打开，自动处理实例复用、栈排序、暂停恢复。暂停用的是引用计数——第一个弹窗打开暂停游戏，最后一个关闭才恢复，中间开关不影响。确认框不走栈，关了还能回到原来的面板。整个框架让业务层只用关心 `OnOpen` 绑定数据和 `OnClose` 清理资源，剩下的全部框架兜底。

## 七、SLG 野外大地图：渲染与建筑管理

> 面试官听到"SLG + 野外大地图"会追问三个方向：地图怎么渲染、动态建筑怎么管理、性能怎么保证。八年经验的回答不能停在"用了瓦片地图"，要讲清楚分层架构和决策链条。

### 7.1 先定技术路线：为什么不用 Unity 的 Tilemap 直接铺

SLG 野外地图的规模跟普通 2D 游戏不是一个量级——动辄 2000×2000 格甚至更大。如果一次性铺满所有格子：

- 几千个 Tile 的 GameObject → 内存炸、Draw Call 炸
- 玩家通常只看屏幕内 ~30×20 格 → 99% 的 Tile 在浪费渲染

所以核心思路是**只渲染玩家视野范围内的东西**，范围外的只保留数据、不保留渲染对象。

### 7.2 分层架构

野外地图拆成四层，每层独立管理：

```
┌─────────────────────────────────────┐
│  第四层：UI 标记层                    │  ← 地名、坐标、行军线、选中框
│  (Canvas / Screen Space Overlay)     │     渲染方式：uGUI
├─────────────────────────────────────┤
│  第三层：动态建筑 / NPC 层            │  ← 城池、野怪刷新点、采集点
│  (对象池管理，按需显示/隐藏)           │     渲染方式：Sprite + Animation
├─────────────────────────────────────┤
│  第二层：地图装饰层                    │  ← 树、石头、河流、山脉
│  (跟随地形表，静态批量渲染)            │     渲染方式：Sprite Atlas 合图 + 静态合批
├─────────────────────────────────────┤
│  第一层：地形底层                      │  ← 草地/沙漠/雪地，按坐标切换
│  (大图 + 九宫格切分 / 动态 Tile)       │     渲染方式：Texture Atlas
└─────────────────────────────────────┘
```

### 7.3 地形底层：一张大图怎么省

2000×2000 格的地图，每格一张小图显然不现实。两种方案：

**方案 A：整张大背景图 + 九宫格切分**

```
把整张地图的底图（如 8192×8192 PNG）切成 256×256 的小块
→ 只加载屏幕范围内的 9 块（九宫格）
→ 玩家移动到新区域 → 卸载旧块 → 加载新块
→ 永远只保留 ~9 块在内存里
```

**方案 B：动态 Tile 渲染（更灵活，但更复杂）**

```
地图数据存为二维数组 mapData[x][y] = 地形类型（0=草地, 1=沙漠, 2=水...）
→ 计算屏幕视野覆盖哪些格子
→ 只创建视野范围内的 Tile Sprite
→ Tile 走对象池复用——移到视野外时回收
```

**实际项目更可能是 A+B 混用**：底图用大图切块（省 Draw Call），地形变化区域（被攻击后的焦土、季节变化的植被）用动态 Tile 叠加。

### 7.4 动态建筑：城池、野怪、采集点的管理

这是面试官最爱挖的——"地图上几千个城池你怎么管理？"

**数据结构**：

```
不是每个建筑一个 GameObject，是每个建筑一条数据记录 + 视野内才实例化。

数据层（常驻内存）：
  MapBuildingData[] allBuildings = [
    { id: 1001, type: "city", gridX: 150, gridY: 320, level: 5, owner: "玩家A" },
    { id: 1002, type: "monster_spawn", gridX: 155, gridY: 322, level: 3, ... },
    ...几千条...
  ]

渲染层（视野驱动）：
  1. 玩家移动 → 计算当前视野覆盖哪些格子
  2. 查询 allBuildings 在这些格子范围内的
  3. 从对象池取 Sprite → 放到对应坐标 → 显示
  4. 移出视野的 → SetActive(false) 回池
```

**为什么不做每一个 GameObject**：几千个 GameObject 光 `Update` 空转就吃 30% CPU。数据记录只有 100 字节，几千条才几百 KB。渲染对象只在视野内几十个。

**建筑状态切换**：

```csharp
// Cocos Creator 里的典型结构
class BuildingView {
    // 状态驱动，不是每帧更新
    public void SetState(BuildingState state) {
        switch (state) {
            case BuildingState.Constructing: ShowConstructingAnimation(); break;
            case BuildingState.Idle:         ShowIdleSprite(); break;
            case BuildingState.Upgrading:    ShowUpgradeEffect(); break;
            case BuildingState.Damaged:      ShowDamagedSprite(); break;
        }
    }
}

// 服务端推送 → 客户端改数据 → 如果该建筑在视野内 → 切状态
// 如果不在视野内 → 只改数据，下次进入视野时按最新状态创建
```

### 7.5 性能优化三板斧

**① 视野裁剪（核心）**

```
玩家在 (gridX=100, gridY=100)
屏幕可看 20×15 格
→ 只处理 gridX ∈ [90, 110] 且 gridY ∈ [93, 107] 的对象
→ 范围外：数据在，渲染不在
```

**② 对象池**

```
建筑/怪物/特效 → 全走池
城池 Prefab (max 20)       → 视野内最多 20 个城池
野怪栏 Prefab (max 50)      → 视野内最多 50 只
行军特效 (max 10)           → 视野内最多 10 条
```

**③ 脏标记 + 按需刷新**

```
建筑数据变更时：
  1. 更新数据记录（几字节操作）
  2. 检查：这个建筑当前在视野内吗？
    → 在：更新渲染状态
    → 不在：只改数据，不碰渲染

不每帧遍历所有建筑、不每帧刷新所有 Sprite
```

### 7.6 大地图的坐标系转换

SLG 地图通常用**格子坐标**而非世界坐标：

```
格子坐标 (gridX, gridY) ←→ 世界坐标 (worldX, worldY)

gridToWorld(gx, gy) = (gx * tileWidth + offsetX, gy * tileHeight + offsetY)
worldToGrid(wx, wy) = ((wx - offsetX) / tileWidth, (wy - offsetY) / tileHeight)

// 例子：六边形格子（很多 SLG 用六边形）
// 奇数行和偶数行有半个格子的 X 偏移
float ox = (gy % 2 == 0) ? 0 : tileWidth / 2;
worldX = gx * tileWidth + ox;
```

### 7.7 Cocos Creator 项目里的实际做法（对应《御剑三国》）

结合你的从业经验，可以这样讲：

> 《御剑三国》的野外地图分了四层管线。**底层**是大图切成 256×256 的块，按九宫格加载——玩家视野周边 9 块常驻，其余卸载。**装饰层**跟随地形表，用 Sprite Atlas 合图 + 静态合批，同屏数百棵树只走个位数 Draw Call。**建筑层**是核心——地图上几千个城池、野怪点、采集点，不可能当 GameObject 全铺。每条数据在内存里只是结构体，只有在视野范围内的才从对象池实例化渲染。服务端数据变更时做脏标记检查——在视野内就刷新渲染，不在就只改数据，下次进视野时自然是最新状态。**UI 标记层**放地名、行军线、选中框，走 uGUI 独立 Canvas。

### 7.8 面试追问预案

**Q: 城池升级/建造中的动画怎么同步？**

> 城池状态由服务端下推——`{ buildingId: 1001, state: "upgrading", remainSeconds: 300 }`。客户端收到后更新数据、检查是否在视野内、在的话播升级动画 + 倒计时。不在视野内只记数据，玩家自己滑过去看的时候已经是最新状态。倒计时走本地时间——误差几秒在 SLG 里不影响体验，如果玩家切后台回来，重新跟服务端对一次时间就行。

**Q: 几千条建筑数据的查询怎么做？**

> 不是每次移动遍历全部数据。按格子做了空间分桶——地图切成 64×64 格的块，每个块维护自己的建筑列表。玩家移动时只查所在块及其相邻 8 个块。从遍历 2000 条变成查 9 个桶。

**Q: Cocos Creator 用什么渲染架构？**

> Cocos Creator 的渲染是节点树 + 渲染排序，跟 Unity 的 Canvas/Renderer 类似但更轻量。Batch 渲染靠引擎自动合图——把同一纹理的 Sprite 合到一个 Draw Call。如果引擎自动做不到满意效果，可以用静态合图（提前把装饰树拍到一张大图里）。动态建筑不走静态合图，而是控制同屏实例数量 + 纹理图集控制材质种类。

### 7.9 深入：Cocos Creator 渲染流程与 Draw Call 优化

#### 7.9.1 渲染节点树的完整流程

Cocos Creator 的渲染不是「遍历场景节点 → 逐个画」，而是中间有一个**收集 + 排序 + 合批**的流程：

```
场景节点树（逻辑层）                渲染管线
┌──────────────────┐
│  Scene            │
│  ├─ MapLayer      │
│  │  ├─ Sprite A  (草地纹理)       ─┐
│  │  ├─ Sprite B  (草地纹理)       ─┤ 同纹理 → 1 个 Draw Call
│  │  ├─ Sprite C  (草地纹理)       ─┘
│  │  ├─ Sprite D  (树纹理)         ─┐
│  │  └─ Sprite E  (树纹理)         ─┤ 同纹理 → 1 个 Draw Call
│  ├─ BuildingLayer                 ─┘
│  │  ├─ Sprite F  (城池纹理)       ─┐
│  │  └─ Sprite G  (城池纹理)       ─┤ 同纹理 → 1 个 Draw Call
│  └─ UILayer                       ─┘
│     └─ Label  (字体纹理)          ── 字体 → 1 个 Draw Call
└──────────────────┘

           ↓ 引擎内部

  ① 遍历节点树 → 收集所有 RenderComponent
     (Sprite、Label、Particle、Graphics、MeshRenderer...)

  ② 生成 RenderData —— 顶点/UV/纹理ID/材质/混合模式

  ③ 排序 —— 按（layer → 材质 → 纹理 → Z-order）排序

  ④ 合批 —— 相邻且纹理相同、材质相同 → 合并成 1 个 Draw Call

  ⑤ 提交 —— 按合批后的顺序逐个发 Draw Call 给 GPU
```

**补充：Cocos 3.x 之后的变化**

```
Cocos 2.x:
  节点树遍历 → 排序 → 合批 → 渲染 (传统单线程)

Cocos 3.x:
  节点树遍历 → 收集 → RenderGraph → 多线程剔除 → GPU Driven
  (更像现代引擎的 RenderGraph 架构，不再是简单遍历)
```

#### 7.9.2 Draw Call 被打断的原因（合批失败）

引擎不是万能的——两个用了同一纹理的 Sprite 不一定能合到一起。阻断合批的元凶：

**① 不同纹理 / 图集（最常见）**

```
Sprite A: 用的是 ui_atlas_1.png
Sprite B: 用的是 ui_atlas_1.png  → ✅ 能合批
Sprite C: 用的是 ui_atlas_2.png  → ❌ 打断！切纹理了一次 Draw Call
Sprite D: 用的是 ui_atlas_1.png  → ❌ 又打断！（即使纹理跟 A/B 一样，已经被 C 隔开了）
```

**② 不同材质 / Shader**

```
即使纹理一样，Shader 不同也不能合批
灰色材质 → grayShader  → 1 个 Draw Call
灰色材质 → glowShader  → ❌ 打断！不同 Shader 的渲染状态不同，GPU 必须切换管线
```

**③ 渲染顺序被插入**

```
树 A（草地纹理）
树 B（草地纹理）
Label "赤壁"（字体纹理→ 1 个 Draw Call）
树 C（草地纹理）→ ❌ 打断！虽然纹理跟 A/B 一样，但中间被 Label 隔开了
```

**④ 遮罩 / 裁剪节点（Mask）**

```
Mask 组件内部和外部的节点在不同渲染上下文
→ Mask 内的所有内容 = 至少 2 个 Draw Call（Stencil 写入 + Stencil 测试）
→ Mask 内的节点跟外部的不能合批
```

**⑤ 不同 Blend 模式**

```
常规 Sprite (Blend: SrcAlpha OneMinusSrcAlpha)
特效 Sprite (Blend: SrcAlpha One → Additive)
→ 不同混合模式 → 不能合批
```

**⑥ 九宫格 / 填充模式**

```
普通 Sprite → Simple
九宫格 Sprite → Sliced
→ Cocos 内部用的 Shader 变体不同 → 打断
```

**⑦ Layer / Camera 不同**

```
不同 Layer 的节点走不同的渲染批次
不同 Camera 渲染 → 各自独立提交 Draw Call
```

#### 7.9.3 降 Draw Call 的 9 种手段

| # | 手段 | 怎么做 | 效果 |
|---|---|---|---|
| ① | **自动图集 (Auto Atlas)** | 把同场景/同模块的小散图配置到自动图集中 → 引擎构建时自动合成大图 | 50 张小图 → 1 张大图 → 减少几十个 Draw Call |
| ② | **纹理图集 (Texture Atlas)** | 美术出图时就合好，或构建工具合成。同一个 Atlas 里所有的 Sprite 天然可合批 | 根本性方案 |
| ③ | **调整节点顺序** | 把用同一纹理/图集的节点在层级树里靠在一起，不要被其他纹理的节点隔开 | 修复"打断了但本质上能合"的情况 |
| ④ | **静态合图 (Static Batching)** | 引擎把不动的节点（树、石头、建筑外墙）标记为 Static → 构建时合并成一个大 Mesh → 一次提交 | 场景装饰物从几百个 Draw Call 降到个位数 |
| ⑤ | **Bitmap Font / 字符图集** | UI 文字不用系统字体，用 Bitmap Font 或 SDF 字符图集 → 多段文字共享同一张字符纹理 | 大量文字场景（聊天、战报）效果明显 |
| ⑥ | **减少 Mask 使用** | 能不 Mask 就不 Mask → 用 Rect 裁切代替圆角遮罩 → 或在纹理层面画好形状 | 每个 Mask = 至少 +2 Draw Call |
| ⑦ | **合并材质** | 把用了同一纹理但不同材质参数的节点统一材质（用 MaterialPropertyBlock 或直接共用） | 减少材质切换 |
| ⑧ | **关闭不需要的 Alpha** | UI 背景图、遮罩图 → Opaque 模式 → 渲染顺序更灵活 → 更容易合进前面的批 | 不保证降，但减少打断风险 |
| ⑨ | **分场景 / 分 Canvas** | 战斗场景和 UI 用不同的 Camera → 各自独立的渲染队列 → 互不打断 | 结构性隔离 |

#### 7.9.4 不同场景的优先级

**SLG 野外地图**：

```
自动图集 (①) > 静态合图 (④) > 调整节点顺序 (③)
→ 底层地形 + 装饰树：静态合图，几百棵树 1 个 Draw Call
→ 动态建筑：自动图集，城池/野怪共享纹理
→ 行军线/特效：走图集 + Additive Blend 单独批次
```

**UI 界面**：

```
图集优先 (②) > 减少 Mask (⑥) > Bitmap Font (⑤) > 合并材质 (⑦)
→ 一个界面一张图集，所有按钮/图标/底框在上面
→ 文字走字符图集，不插队
→ Mask 只用于必要场景（ScrollView 列表裁剪）
```

**战斗场景**：

```
静态合图 (④) + 对象池 + 图集
→ 战场装饰静态合批
→ 怪/弹丸走对象池 + 同一图集 → 天然可合并
→ 粒子特效限制数量（本身就是高 Draw Call 消耗品）
```

### 7.10 面试怎么讲（1 分钟版）

> SLG 野外地图的核心思路是数据渲染分离——几十万格的地图，渲染层只看玩家视野那一小块。底层是四层架构：地形底图做大图切块按九宫格加载，装饰层走 Sprite Atlas 合图批量渲染，动态建筑数据常驻但只在视野内从对象池实例化——几千个城池在内存里只是结构体数组，屏幕上只有视野内的几十个渲染对象。建筑状态切换走脏标记——在视野内刷新、不在视野只改数据。查询走空间分桶，按格子块索引，避免全局遍历。
