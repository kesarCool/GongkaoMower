> 这三个话题都是从简历关键词延伸出来的高频追问，面试官听到关键词就会顺着问。

## 一、资源合图批处理 & 纹理压缩

### 1.1 什么是合图（Sprite Atlas / 图集）

**问题**：一个 UI 界面有 50 个小图标，每个图标一张 PNG。每个 PNG 对 GPU 来说是一次独立的 Draw Call（绘制调用）→ 50 次 Draw Call → 渲染管线频繁切换纹理 → 性能差。

**合图的思路**：把 50 张小图拼成 1 张大图，GPU 一次 Draw Call 渲染整张图，用 UV 坐标裁剪显示需要的部分。

```
合图前：50 个文件，50 次 Draw Call
  [icon1.png] [icon2.png] [icon3.png] ... [icon50.png]

合图后：1 个文件，1 次 Draw Call
  ┌──────────────────────────────┐
  │ icon1 │ icon2 │ icon3 │ ...  │
  │──────────────────────────────│
  │ icon16│ icon17│ icon18│ ...  │
  │──────────────────────────────│
  │ ...                         │
  └──────────────────────────────┘
```

**Unity 里的做法**：把图标放入同一个 Sprite Atlas Asset → 打包时 Unity 自动合并 → 运行时用 `sprite.name` 引用，Unity 自动处理 UV 映射。

**为什么叫"批处理"**：不是手动一个一个拖，而是写编辑器工具脚本批量扫描所有图标 → 按尺寸/用途自动分组 → 批量生成 Sprite Atlas → 批量替换引用。一个项目几百上千张图，不批量处理根本做不完。

### 1.2 纹理压缩（个人项目里的实践）

**问题**：一张 1024×1024 的 PNG，RGBA 32-bit，在内存里占 1024 × 1024 × 4 = **4MB**。同屏几十张这样的图，内存直接炸。

**纹理压缩的原理**：不是 PNG/JPEG 那种文件压缩（文件小但加载到内存还是大），而是**改变 GPU 的纹理存储格式**，让纹理在显存/内存里的占用直接变小。

| 格式 | 每像素 | 1024×1024 占用 | 透明度 | 适用平台 |
|---|---|---|---|---|
| RGBA32（原始） | 32 bit | 4 MB | ✅ | 编辑器 |
| **ASTC** 6×6 | ~3.5 bit | ~0.43 MB | ✅ | iOS / Android 主流 |
| ETC2 | 4-8 bit | 0.5-1 MB | ✅ | Android |
| DXT5 | 8 bit | 1 MB | ✅ | PC |
| RGB Crunched | 可变 | 可变 | ❌ | 不需要透明的纹理 |

**效果**：4MB → 0.43MB，直接省了 90%。

**个人项目的实践**：

在微信小游戏里，纹理压缩直接影响分包体积和运行时内存：

```
微信小游戏使用 WebGL 2.0 → 支持 ETC2 / ASTC
Unity Texture Importer 设置：
  - Texture Type: Sprite (2D and UI)
  - Compression: ASTC 6×6（移动端）/ DXT5（PC 开发调试）
  - 不需要透明的图关闭 Alpha 通道 → 再省 25%
```

在 [docs/cdn-analysis.md](docs/cdn-analysis.md) 里有详细的纹理优化记录：bg_01.jpg 从 764KB 压到 188KB、地图纹理集用 ASTC 压缩约 0.5MB、计划中的去除不需要的 Alpha 通道。

**面试怎么讲**：

> Unity 的 Sprite Atlas 把多张小图合成一张大图，减少 Draw Call。纹理压缩是改变 GPU 的纹理存储格式——ASTC 6×6 可以把 4MB 的纹理压到 0.4MB，在显存里直接生效，不是文件级别的压缩。两个手段配合：合图减少渲染切换次数，压缩减少显存占用。

### 1.3 追问：Draw Call 是什么

> CPU 告诉 GPU "画这个东西" 的指令。每次切换材质/纹理/Shader → 就要发一个新 Draw Call。合图的核心目的就是让多个 UI 元素共享同一张纹理 → 减少纹理切换 → 降低 Draw Call。手机游戏通常控制在 100 次以内，超过就开始卡。

## 二、模块化拆分与多语言适配

### 2.1 模块化拆分

**场景**：《御剑三国》同时跑韩服、日服、台服、东南亚服等 10+ 语言区域。如果所有语言的文件混在一起 → 包体巨大、改一个语言可能影响其他语言、运营需求不同步。

**拆分思路**：

```
核心工程（共用逻辑）
├── 战斗系统
├── UI 框架
├── 网络模块
└── 数据表结构（表头统一）

语言/渠道模块（独立打包）
├── 中文简体（zh-CN）
│   ├── 本地化文本表
│   └── 特定 UI 资源（简体字字体/书法风格图片）
├── 日语（ja-JP）
│   ├── 本地化文本表
│   └── 特定 UI 资源（日文字体/和风图片）
└── 韩语（ko-KR）
    ...
```

### 2.2 多语言适配：配置表方案（你说的那种）

```
多语言文本表（Excel / CSV）
┌──────────┬──────────────┬──────────────┬──────────────┐
│ TextID   │ zh-CN        │ en-US        │ ja-JP        │
├──────────┼──────────────┼──────────────┼──────────────┤
│ LOGIN_BTN│ 登录         │ Login        │ ログイン     │
│ SHOP_TTL │ 商城         │ Shop         │ ショップ     │
│ SKILL_01 │ 雷霆一击     │ Thunder      │ 雷撃         │
└──────────┴──────────────┴──────────────┴──────────────┘

运行时：
  string lang = PlayerPrefs.GetString("lang", "zh-CN");
  string text = TableManager.Get("Localization", "LOGIN_BTN")[lang];
  → "登录"
```

**优点**：策划可以直接改 Excel，不需要程序员介入。一条记录能覆盖所有语言，不易漏。

**缺点**：长文本（剧情对话）放 Excel 里很难维护——列太宽、换行乱、不好预览。

### 2.3 Git 分支方案（也是你说的那种）

```
main ← release 分支，不含渠道差异
├── feat/cn-android    ← 国内安卓
├── feat/cn-ios        ← 国内 iOS
├── feat/kr            ← 韩国
├── feat/jp            ← 日本
```

**工作方式**：共用代码在 main，渠道特定改动在各分支。发版时切到对应分支构建。

**优点**：隔离性强，改一个渠道不会影响其他。

**缺点**：分支多了合并地狱——main 改了一个 Bug，10 个分支都要合一遍。

### 2.4 更好的方案：Google Sheet + 自动化管线

这是目前工业级项目（头部 SLG / 二次元手游）用得比较多的做法，结合了你现在的方案但更自动化：

```
Google Sheet（多人协作编辑）
  ↓ 脚本自动导出
JSON / CSV 文件（每个语言一个文件）
  ↓ CI/CD 构建时
打进对应渠道包（不再需要 Git 分支管理渠道）
```

**关键差异**：

| | Excel + Git 分支 | Google Sheet + 管线 |
|---|---|---|
| 翻译协作 | 离线 Excel，邮件传来传去 | 多人实时在线编辑 |
| 渠道管理 | 每个渠道一个 Git 分支 | 构建脚本按参数切语言 |
| 翻译审核 | 手动比对 | API 接入翻译平台（如 Crowdin/Lokalise） |
| 漏翻检测 | 人工检查 | CI 自动比对 key 数量 + 占位符 |
| 长文本 | Excel 列挤成面条 | Google Sheet 单元格也挤，但可以接翻译平台 |

**进阶方案（大厂做法）**：

```
1. 文本 key 管理：Excel → 导出 JSON
2. 翻译：接入 Crowdin / Lokalise API
   - 策划新增 key → 自动推送到翻译平台
   - 翻译人员在线翻译 → 审核通过 → API 回调拉回 JSON
3. 构建：CI 按 target_lang 参数 → 打包对应语言文件 → 生成渠道包
4. 分支策略：只有 main 一个分支，渠道差异靠配置文件 + 构建参数
```

### 2.5 图片/UI 层面的多语言

文字之外还要处理：

- **字体**：中文用中文字体，日文用日文字体，阿拉伯文要 RTL（从右到左）布局
- **图片含文字**：按钮图上的「开始游戏」四个字 → 每个语言要单独出图，或改用 Text 组件实时渲染
- **UI 布局**：德语一个词是中文的 3 倍长 → 按钮要自适应宽度 → 或用缩略版翻译
- **占位符**：`"您获得了 {0} 金币"` → `"You got {0} gold"` → 不同语言 {0} 位置可能不同 → 不能用 `string.Replace`，要用 `string.Format`

### 2.6 面试怎么讲

> 核心是配置表驱动 + 渠道隔离。文本放在多语言配置表里，按 TextID 查询，当前语言由 PlayerPrefs 控制。渠道特定资源（字体、含文字图片）按文件夹分开放。之前用 Git 分支管理渠道差异，后来改成了构建参数 + CI 管线——渠道配置和代码分离，一个分支就能出所有渠道包换。如果需要翻译平台对接，可以接入 Crowdin 或者 Google Sheet 自动导出。

## 三、ProtoBuf vs JSON

### 3.1 先搞清楚：它们都是序列化协议

```
客户端                                服务器
  │                                     │
  │  发送数据：{ "hp": 100, "pos": ...}  │
  ├────────────────────────────────────→│
  │                                     │
  │             收到响应                 │
  │←────────────────────────────────────┤
  │                                     │
```

**协议做的事情**：把内存里的数据结构（类/对象） → 变成一堆字节 → 发给对方 → 对方还原成数据结构。

### 3.2 JSON 怎么做

```json
{
  "playerId": 10001,
  "name": "玩家张三",
  "hp": 100,
  "position": { "x": 12.5, "y": 3.7 },
  "items": [
    { "id": 1, "count": 5 },
    { "id": 2, "count": 3 }
  ]
}
```

**流程**：对象 → `JsonUtility.ToJson()` → 字符串 → `Encoding.UTF8.GetBytes()` → 发出去。收到后反向操作。

**优点**：
- 人类可读，直接看能懂
- 抓包调试方便
- 几乎所有语言都有内置支持

**缺点**：
- **体积大**：字段名重复存储（`"playerId"` 出现两次，`"name"` 占了 6 个字节，实际数据才 12 个字节）
- **解析慢**：字符串解析 → 逐个字符判类型 → 字符串转数字 → 构建对象
- **没有 Schema**：字段拼错只能在运行时发现，编译期不报错

### 3.3 ProtoBuf 怎么做

先定义 `.proto` 文件（Schema）：

```protobuf
message PlayerData {
  int32 player_id = 1;     // 字段用数字编号，不是字符串名
  string name = 2;
  int32 hp = 3;
  Position position = 4;
  repeated Item items = 5;
}

message Position {
  float x = 1;
  float y = 2;
}
```

**流程**：`.proto` 文件 → `protoc` 编译器 → 生成 C# 强类型类 → `PlayerData.ToByteArray()` → 直接发二进制 → 对方 `PlayerData.Parser.ParseFrom(bytes)` → 还原。

**传输的是二进制，不是 JSON 文本**：

```
JSON（文本）：{"playerId":10001,"name":"玩家张三","hp":100}
  → 约 55 字节（取决于编码）

ProtoBuf（二进制）：08 11 27 12 0C E7 8E A9 E5 AE B6 E5 BC A0 E4 B8 89 18 64
  → 约 18 字节（同一条数据）
```

### 3.4 对比

| | JSON | ProtoBuf |
|---|---|---|
| 格式 | 文本字符串 | 二进制 |
| 体积 | 大（字段名重复存储） | 小（数字编号 + Varint 编码） |
| 解析速度 | 慢（字符串解析） | 快（二进制直接映射） |
| 可读性 | 人类可读，抓包直接看 | 二进制，需要工具反序列化 |
| Schema | 无（运行时校验） | 有（`.proto` 编译期校验，字段类型不对编译不过） |
| 版本兼容 | 手写兼容逻辑 | 内置向前/向后兼容（新增字段给默认值） |
| 调试 | 方便（看得懂） | 不方便（需要 proto 文件 + 工具） |
| 适用场景 | Web API、配置文件 | 游戏网络通信、数据存储 |

### 3.5 为什么游戏用 ProtoBuf 而不是 JSON

**第一，包体小 = 流量省 + 延迟低**。MOBA/SLG 每帧同步的数据量，用 JSON 可能 5KB，ProtoBuf 可能 1KB。移动网络不稳定时，1KB 比 5KB 丢包率和重传概率都低得多。

**第二，Schema 是双刃剑——在游戏里是好处**。`.proto` 文件就是前后端的数据合同。服务端改了 `PlayerData` 的字段类型 → C# 编译直接报错 → 不会上线后才炸。JSON 没有这个保护——字段拼错只能在运行时发现。

**第三，版本兼容**。ProtoBuf 的字段编号机制天然支持新增/废弃字段：

```protobuf
message PlayerData {
  int32 player_id = 1;
  string name = 2;        // v2.0 废弃
  int32 hp = 3;
  string display_name = 4; // v2.0 新增——旧客户端收到后忽略，默认空字符串
}
```

旧客户端用旧 proto 解析新数据 → 不认识字段 4 → 跳过，不报错。JSON 做不到——所有字段都会解析，客户端不认识的字段要么忽略要么报错，而且没有 Schema 你不知道哪个字段是新加的。

### 3.6 ProtoBuf 的缺点

- **不可读**：抓包看到一堆十六进制，调试必须配合 proto 文件 decode
- **需要编译步骤**：`.proto` → 生成代码，增加构建流程
- **不适合超小数据**：几个字节的数据 ProtoBuf 的序列化开销可能比数据本身还大
- **动态类型不友好**：必须提前定义消息结构，不能在运行时随意拼 JSON

### 3.7 面试怎么讲

> 游戏网络通信对包体大小和解析速度敏感。ProtoBuf 是二进制序列化，字段用数字编号代替字符串名，用 Varint 变长编码压缩整数——同一条数据比 JSON 小 60-70%。更重要的是有 Schema 约束：`.proto` 文件是前后端的数据合同，字段类型不对编译就报错，不会留到线上炸。向前向后兼容——服务端加字段，旧客户端忽略不认识的，不报错。缺点是不可读、调试需要工具。
