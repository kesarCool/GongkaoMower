### Q2：Cocos Creator 用了几年？2.x 还是 3.x？有什么区别？

**你的实际情况**：禅游用的大概率是 1.x 或 2.x（2018-2020），中青宝用 2.x（2020-2022）。可能没用过 3.x。

**回答策略**：

> 主要用的是 2.x——从禅游的棋牌到中青宝的《御剑三国》都是。2.x 的场景文件是 .fire，组件用 cc.Class 声明，3.x 改成了 .scene + class 语法 + 新的 assetManager。我没实际用 3.x 上过线，但了解核心变化——渲染管线换了、EventTarget 独立出来了、Asset Bundle 替代了 2.x 的 Bundle。引擎切换对我来说不是大问题——Unity 从 2019 到 2021、从 Built-in 到解 SRP 我都跟过。

**风险**：如果面试官追问 3.x 具体细节——诚实说没用过线上项目，但了解变化。

### Q3：做没做过海量用户场景的性能优化？具体做了什么？

**这是你的强项，往死里展开。**

**回答策略**：

> 禅游的棋牌游戏累计 500 万+用户，中青宝的《御剑三国》多渠道同步上线。性能优化我分几层做：

> **包体层面**：资源分包加载——首包只放启动必需的，其余按场景加载。微信小游戏首包限制 4MB，用 WASM 代码分包 + Brotli 压缩把数据包从 17MB 压到可控范围。

> **运行时层面**：做了分帧生成（波次怪物不分一帧全刷，每帧上限 5 个）、对象池复用（子弹/怪物/特效全走池，GC 分配从每帧几十 KB 降到接近零）、索敌注册表（CombatTargetRegistry 替代 FindObjectsWithTag，同屏 100 敌时索敌从 0.5ms 降到 <0.01ms）。

> **渲染层面**：Sprite Atlas 合图降低 Draw Call、30FPS 锁帧（微信用 WX.SetPreferredFramesPerSecond）、降分辨率检测 GPU 瓶颈、低端机自动关粒子和阴影。

> **内存层面**：纹理 ASTC 压缩（4MB → 0.4MB）、音频按场景分组加载/卸载、场景切换时主动清理对象池和注册表。

### Q4：Web 游戏首屏加载怎么优化？

**这是 JD 原文「首屏加载」的追问。**

**回答策略**：

> 首屏加载的核心思路是延迟加载——用户不需要第一眼看到的东西都不进首屏。

> **减少首屏资源**：首屏只放启动 Logo + 登录 UI 必须的图集和字体，其他全部分包。中文字体是体积大头——TMP SDF 字体 7MB，我们做了运行时动态加载 + Prefab 上放轻量占位字体，首屏引用链不碰大字体。

> **代码分包**：业务逻辑拆成多个 Bundle，首屏只加载引擎 + 登录模块。微信小游戏用子包机制（wasmcode 分包 5MB、data-package 分包 17MB）。

> **预加载策略**：用户停在登录页时，后台预加载大厅资源。用户在大厅时，后台预加载战斗资源。

> **骨架屏 / 首屏占位**：不要白屏等加载，用一个极简的静态页面（Loading 图 + 进度条）先撑住，给用户"已经开始了"的感知。

### Q5：你怎么用 AI 工具提升研发效率的？举个具体例子。

**JD 明确要求 AI 工具使用，这是你的差异化优势。**

**回答策略**：

> 我个人项目《文字割草机》全程用了 Claude Code 和 Cursor。最典型的场景是微信小游戏的非 Dev Build 加载失败问题——取消 Development Build 之后游戏卡在启动封面，报 createDataFile undefined。

> 传统排查方式要逐行读 minified 的 framework JS——上十万行。我用 Claude Code 做了八轮诊断：dump 微信 UnityPlugin 闭包内的 processRawData 源码（toString()）→ 分析变量作用域 → 定位到 f.FS 在非 Dev Build 下的正则注入失败 → 验证了外部模块无法写入闭包内变量 → 最终确认在当前 SDK 版本下不可修。整个过程如果纯人工排查，至少多花两天。

> 除了 Debug，用 AI 生成了 Text→TMP 批量转换编辑器工具、Tilemap 像素生成工具这种一次性但繁琐的脚本，写一次跑完不用反复调。

**如果追问"那有什么是 AI 做不到的"**：

> 微信真机环境的调试 AI 帮不了——你必须拿真机跑、看微信开发者工具的日志。另外涉及闭源的第三方 SDK 内部行为，AI 只能辅助推理，最终结论要靠实际验证。
